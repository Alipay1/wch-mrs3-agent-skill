# 任务清单（todowrite）同步要求

界面上的"任务卡"完全来自你调用 `todowrite` 时写入的清单状态：
opencode 只在你调用 `todowrite` 时更新它，其它任何时刻界面都不会被推断或改动。
也就是说——你不更新清单，界面上的进度就停在最后一次写入的状态；
你若一次把多项标成已完成，界面上这些任务就会"同时完成"。
因此请把下列规则当作与"调用工具"同等重要的硬性约束（优先级高于"尽量少调用工具"）：

1. **全量覆盖**：每次 `todowrite` 都要给出**完整清单**，未变动的任务项也必须原样带上。
   只提交变化项会让未列出的任务从界面上消失。
2. **先声明再动手**：开始某个任务项时，在它的**第一个工具调用之前**先调用 `todowrite`
   把该项置为 `in_progress`（同一次清单里：它之前的项为 `completed`、之后的项为 `pending`）。
   不要先执行、事后再补状态——那样界面在整个执行期间都会停在上一项。
3. **做完立即闭环**：该项的实际工作（含必要的验证）做完后**立刻**调用 `todowrite`
   把该项置为 `completed`，同时把下一个要做的项置为 `in_progress`；
   不要连做几项之后再一次性回发。
4. **最后一项也要回发**：最后一项做完后同样要调用 `todowrite` 把它标为 `completed`，
   不要用最终总结代替这次更新（否则界面会一直显示"进行中"直到会话结束）。
5. **一次最多完成一项**：单次 `todowrite` 最多把**一个**非完成项推进到 `completed`
   （其余已完成项维持原状）；确实并行完成多项时也请分次回发，先完成的先回发。
6. **禁止提前完成**：只有确实做完才允许标 `completed`；没做完只能是 `pending` / `in_progress`。
7. **状态字面值**：只使用 `pending` / `in_progress` / `completed` / `cancelled`，
   不要写 `doing`、`done`、`finished`、`wip` 这类变体。
8. **同一时刻通常只有一个 `in_progress`**（确实并行时可多个，但不能借此省略逐项更新）。
9. **`content` 逐字稳定**：同一任务项的 `content` 前后必须完全一致（含标点与空格），
   不要改写措辞、不要重排顺序，新增任务追加在末尾——界面靠它把同一项对应起来。
10. **失败或放弃就明确结束**：用 `cancelled` 结束该项，并在回复中说明原因，不要留着 `in_progress`。

## 正确示例（两个任务：改 A、改 B）

- 动手之前：`[{"content":"修改 A","status":"in_progress"},{"content":"修改 B","status":"pending"}]`
- A 完成、开始 B：`[{"content":"修改 A","status":"completed"},{"content":"修改 B","status":"in_progress"}]`
- B 完成：`[{"content":"修改 A","status":"completed"},{"content":"修改 B","status":"completed"}]`

## 必须避免

- ✗ A、B 都做完才回发一次 → 界面上两项同时变已完成。
- ✗ 只提交变化项 → 未列出的任务从界面上消失。
- ✗ 开工前不回发、事后才补 → 执行期间卡片停在上一项，与思考内容不同步。
- ✗ 最后一项不回发 → 卡片一直显示"进行中"。

这些更新是用户观察进度的唯一途径，请把每次任务推进都视为必须伴随一次 `todowrite` 的固定动作。
