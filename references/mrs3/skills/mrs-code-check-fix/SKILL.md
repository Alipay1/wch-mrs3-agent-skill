# IDE 代码检查修复

用于分析并修复当前 IDE 工程中的 clang-tidy 代码问题。

## 执行流程

严格按照以下顺序执行：

1. 获取当前工程
2. 创建 Todo
3. 第一次 clang-tidy 检查
4. 分析问题并按类型处理
5. 调用 `ide-edit` 修改代码（需要修复时）
6. 第二次 clang-tidy 校验（发生代码修改时）
7. 输出最终报告并结束

其中：

* clang-tidy `Warning` 默认只分析，禁止直接修改；
* 用户明确要求修复 Warning 后，才允许修改；
* 发生代码修改后，必须再次执行 clang-tidy；
* 最终报告必须是本轮最后一次文本输出。

## 1. 获取当前工程

每次执行新的代码检查或修复任务时，**第一个工具调用必须是**：

`ide-get-projectToOperate`

后续检查、源码读取和修改必须基于该工具返回的工程路径，禁止直接使用本地工作目录。

禁止根据历史会话或当前目录猜测工程。

如果未获取到有效工程，则停止执行并提示用户选择工程。

如果用户仅要求查看当前工程，则调用该工具后直接返回结果。

## 2. 创建 Todo

获取工程成功后，必须调用 `todowrite` 创建本次任务的 Todo。

代码修复任务至少包含：

1. 第一次 clang-tidy 检查
2. 分析问题
3. 修改代码
4. 第二次 clang-tidy 校验

仅分析 Warning 时至少包含：

1. clang-tidy 检查
2. 分析 Warning

其中：

* 发生代码修改时，“第二次 clang-tidy 校验”必须作为独立 Todo 项；
* 执行过程中必须根据实际进度同步更新 Todo 状态。

## 3. 第一次 clang-tidy 检查

调用：

`ide-get-project-problems-by-clang-tidy`

`projectPath` 必须使用 `ide-get-projectToOperate` 返回的当前工程路径。

工具返回 `taskId` 后，必须调用：

`ide-get-task-status`

持续查询直到取得最终成功或失败结果。

任何返回 `taskId` 的 IDE 工具，都必须通过 `ide-get-task-status` 获取最终结果后才能继续。

## 4. 分析问题并按类型处理

取得 clang-tidy 最终结果后：

* 整理问题类型、文件、位置和诊断信息；
* 必要时读取相关声明、头文件或调用代码；
* 分析问题根因并确定可能的修复方式。

禁止仅根据 clang-tidy 诊断文本直接修改代码。

不得进行与当前问题无关的重构、格式化或业务逻辑修改。

分析完成后按问题类型处理：

### Warning

* 只分析问题并给出可能的修复方案；
* 禁止修改代码；
* 禁止执行第二次 clang-tidy；
* 直接进入最终报告。

**即使已经能够确定修复方式，也禁止自动修改 Warning。**

只有用户在报告后**明确要求修复 Warning**，才允许进入修复流程。

用户后续要求修复时，视为新的修复任务，仍必须从 `ide-get-projectToOperate` 开始执行完整流程。

### Error

完成分析后进入代码修改流程。

### Error 和 Warning 同时存在

* 仅修复 Error；
* Warning 只分析并写入最终报告；
* 禁止在修复 Error 时顺带修改 Warning。

## 5. 修改代码

仅对允许修复的问题执行修改：

* 必须使用 `ide-edit` 修改已有文件；
* 禁止调用 `edit`、`write`、`bash` 等其他工具修改文件；
* 保持最小修改。

**如果当前仅存在未被用户明确要求修复的 Warning，禁止进入本步骤。**

**如果 `ide-edit` 调用失败，停止后续修复流程，直接输出失败报告并结束本轮对话。**

修改成功后，必须立即进入第二次 clang-tidy 校验。

## 6. 第二次 clang-tidy 校验

只要本次任务发生代码修改，就必须再次调用：

`ide-get-project-problems-by-clang-tidy`

使用同一个当前工程路径，并获取新的 `taskId`。

随后通过：

`ide-get-task-status`

持续查询直到取得最终结果。

第二次 clang-tidy：

* 必须生成新的检查任务；
* 不得复用第一次检查结果。

如果仍存在 Error，则继续分析和修改，修改后再次执行 clang-tidy 校验。

第二次检查中新出现或仍存在的 Warning，不得自动修复，仍按 Warning 规则处理。

## 7. 输出最终报告并结束

所有检查、分析和必要修复完成后，先检查一次 Todo 状态，再输出最终报告。

最终报告必须严格使用以下结构，标题和顺序不得修改或省略，无对应内容时填写“无”或“未执行”：

```markdown
## 代码检查报告

### 检查结果
...

### 问题分析
...

### 处理情况
...

### 最终校验
...
```

报告内容基于实际工具结果：

* 检查结果：说明问题类型及概况；
* 问题分析：说明问题原因和可能的修复方案；
* 处理情况：说明实际修改内容，未修改时说明原因；
* 最终校验：说明最后一次 clang-tidy 结果，未执行时填写“未执行”。

发生代码修改时，必须以**最后一次 clang-tidy 结果**判断目标问题是否修复成功。

**最终报告必须是本轮最后一次输出。报告开始输出后，禁止再调用任何工具或继续输出。**

## 核心约束

* 第一个工具必须是 `ide-get-projectToOperate`
* 工程路径必须使用 `ide-get-projectToOperate` 的结果
* 获取工程后必须创建 Todo
* 异步工具返回 `taskId` 后必须查询最终状态
* 必须先 clang-tidy 检查，再读取源码分析
* Warning 默认只分析，禁止自动修改
* 只有用户明确要求修复 Warning 后才能修改
* Error 修复时禁止顺带修改 Warning
* 修改代码必须使用 `ide-edit`
* 发生代码修改后必须再次执行 clang-tidy
* 本 Skill 不主动调用 `ide-decorate-diffs`
* 输出报告前必须检查一次 Todo 状态
* 最终报告必须严格使用固定格式并作为本轮最后一次输出
