# STM32F103 工程 → CH32V203 工程 迁移指南

## 适用前提

- 源工程基于 **STM32F10x 标准外设库（SPL）**，不是 HAL / LL / 寄存器直写工程。
- 目标芯片是 **CH32V20x**（D6 / D8 / D8W）。若目标是 CH32V103，改用另一套技能。
- **源工程的 SPL 是官方 V3.5.0 原版** —— 本技能的映射表与差异清单按此版本建立
  （`__STM32F10X_STDPERIPH_VERSION = 0x03500000`，见 `stm32f10x.h:135-142`）。
  **进入阶段 1 之前**（走入口 A 即**阶段 0.3 校验通过之后**；入口 B 无阶段 0）读一次
  **`.mrs/originalKeilFiles/stm32f10x.h`** 的版本宏确认：
  - **一致** → 基准版本相符，全程按本技能执行；
  - **不一致**（其它版本）→ 改名表与差异清单**只作参考**，
    涉及部分按「参考文件覆盖不到时怎么办」逐处对照两侧源码。
  - 🔴 **不要早于阶段 0 的工程级转换去读 ST 源码** —— `.mrs/originalKeilFiles/` 由该转换步骤
    导入生成，在那之前它**还不存在**；此时也**不要**去读源工程目录（落点唯一，见下条）。
  - ⚠ 该目录走**入口 B** 时不存在，按下方「读取落点」条目的兜底处理。
  - ⚠ **版本宏只判版本、判不出本地改动** —— 用户改库函数体、改头文件里的宏值，都不会动这个宏。
    **库是否被本地修改，由交付前的「已用符号功能一致性复核专项」负责检出**，
    不靠版本宏、也不靠迁移过程中的偶然发现。
- **开工后不要删除或移出 ST 库源文件** —— 「已用符号功能一致性复核」需要读它对照；
  `05_migration-rules.md` 第二节第 3 项只要求把它**移出编译列表**，不是从工程目录里删掉。
  工程里保留下来的 ST 库源文件**始终不删**（它和 `.mrs/` 下那份副本是两个对象，见下条）。
- **ST 库源码的读取落点 = 新工程根目录下的 `.mrs/originalKeilFiles/`** ——
  ⚠ **先分清两个对象，不要混**：上一条说的是**工程里保留下来的 ST 库源文件**
  （只移出编译列表，**永不删除**）；本条说的是**转换工具放进 `.mrs/` 的那份副本**
  （临时产物，**交付前删除**）。**编译列表里没有它，也不会删工程里的库文件。**
  工程级转换会把**原始 Keil 工程文件**（含 ST 外设库源码、用户代码）整体放进这里。
  凡需要读 ST 侧源码（`.h` 宏值 / 结构体 / `.c` 函数体）时**一律到这个目录读**，
  不要向用户索要源工程路径、不要读源工程目录、不要凭记忆推断。三条性质：
  - **只读** —— 它是「对照物」，**不得编辑**，改了就失去比对基准；
  - **不入编译列表 / include 路径** —— 它在 `.mrs/` 下，本就不参与构建，不要手动加进去；
  - **交付前随该目录一起删除**（见阶段 4.4）—— 删除后若仍需回查，重新执行工程级转换即可再次生成。
  - 该目录**不存在**时（走「入口 B」或转换工具未生成）：**停下向用户索要 ST 库源码
    或请其重新执行工程级转换**，不要凭记忆补。

**两条入口，按工程当前状态选：**

| 入口 | 触发条件 | 起点 |
|---|---|---|
| **A：从 Keil 工程出发**（常规） | 用户给的是 `.uvprojx`，还没有 CH32V203 工程 | **阶段 0** 建工程 → 阶段 1–4 |
| **B：工程已存在** | MRS 里已有 CH32V20x 工程骨架、用户代码已就位（`User/` 下含 `main.c`、`ch32v20x_it.c/h`、`system_ch32v20x.c/h`、`ch32v20x_conf.h`） | 跳过阶段 0，直接从**阶段 1**开始 |

「把 STM32F103 工程转换成 CH32V203 工程」这类一句话请求，走**入口 A**。

本次迁移的全部结论来自对两套库的四维逐项比对（宏 / 寄存器 / 结构体 / 函数，共 19 个共有外设）——
STM32 侧为 **官方 SPL V3.5.0**、CH32 侧为 **CH32V20x EVT**；原始数据与判定过程见 `references/` 目录。

## 最重要的一条原则

**「改名」和「改逻辑」是两件不同的事，先判定再动手。**

| 判定 | 含义 | 处理 |
|---|---|---|
| 目标库无此符号 | 编译报未声明 | 查映射表改名 |
| 同名同义、仅编码不同 | 两侧数值可能不一样 | **不要动**——用宏名即正确 |
| 同名但语义已变 | 名字一样、含义被换 | 必须重做逻辑 |
| 用户代码绕过符号名 | 直接写数值/地址/位带 | 查 `references/07_pointer-and-bitband.md` |
| 签名相同、函数体行为已变 | 名字一样、编译照过 | 查 `references/08_func-behavior.md` |

第二类是本次移植最容易做错的地方。`DBGMCU_TIM1_STOP` 在 STM32 是 `0x400`、在 CH32 是 `0x1000`，
但两侧同名同义，代码里保留宏名**自动就是对的**。此时去「修正」这个差异反而会引入 bug。

第四类反过来：**编译器一句话都不会说**。改名错了编译器报「未声明」，地址写错了没有任何提示。
这一类必须逐条人工核对，且最终只能靠真机验证 —— 见阶段 3B。

全库范围内「同名但语义已变」的只有 **3 项**（NVIC 优先级分组 2 项 + USB 时钟源 1 项），
另加 1 项需按硬件确认（`HSE_VALUE`）。不要把它们和那 22 项无害的编码差异混在一起处理。

最后一类还有一层：**函数签名零冲突，但函数体内部的行为已经变了**。这类差异既不在宏层、
也不在结构体层，而是藏在实现里 —— 共 **76 条**，见 `references/08_func-behavior.md`。
它和第 2 类一样是「编译器一句话都不会说」，但**处理方式相反**：第 2 类不要动，
这一类必须按结论逐条处理。

## 参考文件覆盖不到时怎么办

本技能的结论来自**两套库的逐项比对**：19 个共有外设（宏 / 寄存器 / 结构体 / 函数四维），
以及 CH32 USB 库的重点核实。**不覆盖**用户自定义代码、第三方中间件、比对时未纳入的模块。

⚠ **边界要说清**：「用户自定义代码」指用户**自己新建的 `.c` / `.h`** —— 它们本来就由阶段 2–3
整体迁移，不存在「与基线对照」的问题；**不含用户对 ST 外设库本身的修改**。库一旦被本地改过，
本技能关于该文件的结论即失效，须由「已用符号功能一致性复核专项」检出，并把该改动纳入迁移范围。

遇到参考文件里查不到的差异，**既不臆造、也不跳过**，按顺序补齐：

1. **两侧源码对照（首选依据）** —— ST 侧读**新工程根目录下 `.mrs/originalKeilFiles/`**
   （工程级转换导入的原始 Keil 工程文件，含 ST 外设库源码），CH32 侧读目标工程的库目录，
   两份逐段对照。两侧源码都在手上时，这条**优先于本技能的任何参考文件**；
   **直接读即可，不需要向用户索要**。
   该目录**不存在**时（入口 B、或转换工具未生成）→ 请用户提供源工程路径、或请其重新执行
   工程级转换；仍拿不到就按下文第 3 点处理（标「未确认」并询问用户），**不得凭记忆推断**。
2. **知识库与官方例程** —— 检索 MRS 智能体自带的知识库，
   并对照 `CH32V20xEVT/EVT/EXAM/` 下对应外设的官方例程，以官方例程的实际写法为准。
3. **仍不能确定** —— 标为「未确认」并**询问用户**，不得写进结论。
   尤其**不得**据第三方移植文档的描述或截图推断 —— 这类文档会有错。
   工作目录里那份《从 STM32F103C8T6 移植到 CH32V203C8T6》及其 docx 版本
   （`ch32v203替换stm32f103.docx`）**内容同源**，已核实其中一处事实性错误：
   写「`PADDRx` 对应 `CMAPx`、`MADDRx` 对应 `CPARx`」，而两侧源码按结构体偏移核对
   应是 `PADDR`↔`CPAR`（外设地址）、`MADDR`↔`CMAR`（存储器地址），且 `CMAPx` 系笔误。
   该文档只到「签名 / 位定义」层，**不覆盖函数实现层**，不能替代 `08_func-behavior.md`；
   可以取用它的结论，不能取用它的推断方式。

**前提校验**：本技能的 ST 侧结论取自**官方 SPL V3.5.0**（见上文「适用前提」）。
迁移中凡发现 **`.mrs/originalKeilFiles/`** 里源工程的 ST 库源码与 `references/08_func-behavior.md`
描述的「ST 侧行为」不符，即说明该文件被用户**本地改过** —— 此时**以用户实际代码为准**，
不套用本技能结论，并把该改动本身一并纳入迁移范围。

**这类改动不靠「碰巧读到」来发现**：交付前由「已用符号功能一致性复核专项」系统检出，
它覆盖改函数体 / 改宏值 / 增删库文件三种形态，范围是**用户代码实际用到的外设库函数**。

USB 是这条原则的典型场景（技能包对它的覆盖面有限），见 `references/10_usb-migration.md` 第八节。

## 执行流程

### 阶段 0：工程级转换（仅入口 A）

目标：把 Keil 工程变成可用的 CH32V203 模板工程，后续阶段再往里改库调用。

**0.1 先收齐参数 —— 缺一个就问用户，不要猜**

| 参数 | 说明 | 缺失时 |
|---|---|---|
| 源工程路径 | 源 `.uvprojx` 的完整路径 | **必须询问** |
| 目标路径 | 新工程存放的目录 | **必须询问** |
| 目标工程名 | 新建工程的名字 | **必须询问** |

另外要确定**目标型号**。用户未指定时：先读源工程的 Device 字段定出 F103 型号，
再按封装映射（`references/09_model-mapping.md`）。**V203 侧无对应封装时停止并降级提示**，
不要自行改封装。

**0.2 调用工程级转换**

把上述三个参数交给 MRS 智能体内置的工程级转换能力即可，**不要自己解析 `.uvprojx`
或手工新建工程**。它会：解析 Keil 工程 → 新建 V203 模板工程并删除 `user` 目录下的 `main.c`
→ 过滤保留用户代码，把源文件与头文件加入模板工程 → 修改工程属性（如 include 路径）并自动导入
→ **把整份原始 Keil 工程文件（含 ST 外设库源码）放进新工程根目录下的
`.mrs/originalKeilFiles/`** —— 这是读 ST 库源码的**唯一落点**（见「适用前提」），
**只读、不入编译列表，交付前随该目录删除**（见阶段 4.4）。

**0.3 校验产出（必做）**

| 检查项 | 通过标准 |
|---|---|
| 模板工程结构 | 具备 `User/`、`Startup/`、库目录（`Peripheral/` 等）、链接脚本 |
| 模板 `main.c` 已删 | 模板自带 `main.c` 不再存在，避免与用户 `main` 冲突 |
| 用户 `.c` 已导入 | 源工程源文件逐个出现在工程与编译列表中 |
| 用户 `.h` 已导入 | 就位，且 **include 路径已包含其所在目录** |
| 型号宏 | 与目标型号匹配（`09_model-mapping.md` §1.4） |
| 启动文件 / 链接脚本 | 是 CH32V20x 的，不是 STM32 的 |
| **ST 源码副本** | 新工程根目录下存在 `.mrs/originalKeilFiles/`，且能读到原始 Keil 工程文件（`stm32f10x.h`、`stm32f10x_*.c`、用户代码） |

任一检查项不通过 → **停下报告缺项**，不要带半成品进入阶段 1。
**末行「ST 源码副本」例外 —— 它不阻断**：缺失时**记录并继续**（阶段 1–3 主要靠参考文件），
但到阶段 3C 的 🟠 项与复核专项梯次 B/C 需要读 ST 源码时必须拿到，
届时按「参考文件覆盖不到时怎么办」第 1 条处理（向用户索要或请其重跑工程级转换）。

### 阶段 1：工程基线（先做，且必须做全）

按 `references/05_migration-rules.md` 第二节逐条执行：头文件换名、内核头文件换成 `core_riscv.h`、
移除 STM32 库源文件、确认型号宏（**D6 免配置**）、检测浮点打印、清理 `assert_param`/`IS_*`、给所有中断服务函数补
`__attribute__((interrupt("WCH-Interrupt-fast")))`、补 `SystemCoreClockUpdate()`、
换启动文件与链接脚本。

**型号宏：D6 目标（V203 全系）不需要任何定义。** `ch32v20x.h:19-24` 在三个型号宏均未定义时
会自动 `#define CH32V20x_D6`，这是 WCH 的官方默认路径（EVT 中 176 个 D6 工程无一显式定义），
**不要为此去改工程属性文件**。仅当目标是 **D8 / D8W（V208 / V203RBT）** 时才需显式生效：
改 `ch32v20x.h:20-22` 那三行注释即可（顺序安全，可直接操作）。
⚠ **禁止放进 `ch32v20x_conf.h`** —— 它由 `ch32v20x.h:4881`（文件末尾）才包含，
而设备头自身的 D8/D8W 条件编译在 `:30 / :116 / :125 / :749 / :794 / :874 / :930`，根本看不到。

### 阶段 2：机械替换

按 `references/01_regmap.md`（寄存器位定义宏，1771 项）与 `references/02_structmap.md`
（寄存器结构体成员，22 个结构体）批量改名。这部分是体力活，**全部是编译期错误，可依赖编译器兜底**。

同时按 `references/03_semantic-gaps.md` 第五节（仅 STM32 存在的函数）与第七节
（仅单侧存在的功能宏）清理目标库不存在的函数调用与宏。

### 阶段 3：语义替换（只有 5 项，但必须人工判断）

只处理 `references/05_migration-rules.md` 第三节的 5 项：

1. NVIC 优先级分组——**唯一需要重做逻辑的模块**。CH32 只有「关闭嵌套 / 开启嵌套」两组，
   STM32 的 `Group_2`~`Group_4` 无对应，抢占优先级需重新压缩，依赖多层嵌套的设计需与用户确认。
   注意这两个宏**编译期互斥**：默认配置（嵌套开启）下只定义 `NVIC_PriorityGroup_1`，
   用户代码若用 `NVIC_PriorityGroup_0` 会直接编译报错（fail-fast，按编译错误处理即可）。
2. `HSE_VALUE`——两侧默认值都不可信，必须改为用户板实际晶振频率。无法确认时**询问用户**。
3. `RCC_USBCLKSource_PLLCLK_Div1`——用宏名等价，裸值 `0x00`/`0x01` 含义互换。
4. 用户代码中的裸位掩码——逐个核对（裸地址与位带另有专项，见下）。
5. **系统主频**——迁移后工程的主频必须与原工程一致，**口径是 HCLK / `SystemCoreClock`**。
   72 MHz 源工程的推荐做法是 CH32 选 144 MHz 档 + `RCC_HPRE_DIV2` → HCLK 仍 72 MHz，
   PCLK2/PCLK1 与原工程相同、零重算；带 USB 时主频受 48/96/144 MHz 约束。
   详见下文「主频与时钟配置专项」。

### 阶段 3B：裸地址与位带专项排查

有一类代码绕过符号名直接碰硬件地址：**地址指针直访寄存器**和**位带操作**。
它们的共同点是**编译器不会报错**——改错宏名编译器会拦，改错地址不会。
因此必须人工核对，不能靠编译结果兜底。

按 `references/07_pointer-and-bitband.md` 执行：

**先扫描定位，再逐条改写。** 用技能包内的 `scripts/scan_regaccess.py` 扫一遍用户代码，
它会把裸地址、位带宏、位带别名地址、`NVIC->` 直访、`BSRR` 清零写法全部列出来，
并给出 `文件:行号` 与处理建议。

有 Python 时用 `scan_regaccess.py`（首选）：

```bash
python scripts/scan_regaccess.py <用户代码目录>          # 详细清单
python scripts/scan_regaccess.py <用户代码目录> --quiet   # 只看分类统计
```

机器上没有 Python 时，用等价的 PowerShell 版本 `scripts/scan_regaccess.ps1`
（Win7 起系统自带 PowerShell，无需安装任何东西；两者输出逐字一致，实测
1615 个文件 / 444 处命中完全对齐）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/scan_regaccess.ps1 <用户代码目录>
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/scan_regaccess.ps1 <用户代码目录> -Quiet
```

⚠ **`-ExecutionPolicy Bypass` 不能省**。Windows 默认执行策略是 `Restricted`，
不加这个开关脚本根本起不来，会报 `PSSecurityException: 无法加载文件...禁止运行脚本`。
这是调用方（命令行）的事，脚本自身不做任何策略探测或自我修复。

两个脚本都只做文本模式匹配，宏展开后的间接用法可能漏检，结论要配合
`references/07_pointer-and-bitband.md` 人工复核。

1. **地址指针直访寄存器**——外设基址与 STM32F10x **完全相同**（35 项逐一核对），
   寄存器偏移在 19 个结构体中 17 个完全一致，另 2 个只在尾部有增减，
   **没有任何「两侧都有的寄存器」发生错位**。结论是**裸地址数值可以直接沿用**；
   但仍建议改回符号名（如 `*(volatile uint32_t*)0x4001080C` → `GPIOC->OUTDR`），
   让编译器接管后续检查。
2. **位带操作**——CH32 是 RISC-V 内核，**整颗芯片没有位带硬件**，
   `PERIPH_BB_BASE` / `SRAM_BB_BASE` 在 CH32 侧根本不存在，对 `0x42000000` 段的
   读写没有定义。所有位带用法必须改写：GPIO 优先用 `BSHR` / `BCR`
   （硬件原子，与位带语义等价），其它外设用读-改-写；确实需要原子性时用
   `core_riscv.h` 的 `__AMOOR_W` / `__AMOAND_W`（`ch32v20x.h` 已包含该头文件）。
3. **位带别名地址可以反解**：`偏移 = (别名地址 - 0x42000000) >> 5`，
   `位号 = ((别名地址 - 0x42000000) >> 2) & 0x1F`。参考文件里已把 STM32 库内部
   用到的 37 个别名地址全部反解成「寄存器地址 + 位号」，可直接查表。
4. 🔴 **一处静默陷阱**：STM32 的 `GPIOA->BSRR = (1 << (n + 16))` 是清零写法，
   但 CH32 的 `BSHR` 只有置位定义（`BS0`~`BS15`），没有高 16 位清零语义。
   这类代码必须改写为 `GPIOA->BCR = (1 << n)`，**不能只把寄存器名改掉**。

### 阶段 3C：函数实现层核对

前两个阶段处理「名字」，3B 处理「地址」，这一阶段处理**函数体**。

函数原型在两侧**零签名冲突**（403 个原型，见 `references/04_api-delta.md`），
所以改名改完之后全部能编译 —— 但 **76 个函数的实现已经变了**，编译器不会给任何提示。

按 `references/08_func-behavior.md` 执行。该表把 19 个外设的 76 条差异逐条给出
「迁移动作 + 依据」，并单独拎出 6 条最容易静默出错的：

1. **GPIO：GPIOC 的引脚重编号依赖调用顺序** —— 它的开关是文件级全局 `MCU_Version`，
   **只在 `GPIO_Init()` 内赋值一次**，另外 9 个函数只读不写。在任何 `GPIO_Init()` 之前
   对 GPIOC 的库函数调用**不会重编号**；且裸地址 / 位带直访 GPIOC **完全不参与重编号**，
   与库函数路径结果不一致。
2. **`SPI_StructInit` 不初始化 `SPI_NSS`** —— STM32 写 9 个成员、CH32 只写 8 个，
   该成员会**残留未初始化的栈值**。结构体初始化后须手工补 `s.SPI_NSS = SPI_NSS_Hard;`。
3. **`FLASH_GetStatus` / `FLASH_GetBank1Status` 删掉 PGERR 分支** —— `FLASH_ERROR_PG`
   永不返回，编程失败判断改为「非 `FLASH_COMPLETE` 即失败」。
4. **`NVIC_PriorityGroupConfig` 不写硬件** —— 只存全局变量，必须**先调它、再调 `NVIC_Init`**，
   顺序颠倒分组不生效。
5. **`DBGMCU_GetREVID` / `DBGMCU_GetDEVID` 返回值互换** —— 要取版本号反而应调 `GetDEVID`。
6. **DMA 标志/中断查询函数固定只读 `DMA1`** —— 传 `DMA2_*` 参数不报错，但读到错的寄存器。

⚠ 本阶段**不能靠编译结果兜底** —— 这些改动改与不改都能编译通过。核对完成后仍需真机验证。

> **本阶段与「已用符号功能一致性复核专项」的分工**：本阶段按 `08_func-behavior.md` 的**清单**走
> （库侧 76 条已核实差异，静态覆盖全部 19 个外设）；专项按**用户代码实际用到的库函数**走
> （交付前在阶段 4.3 执行）—— 只有它能检出「**用户改过 ST 库**」这一类，因为清单里的差异是
> **官方固有**的，与「用户改动」性质不同。两者都要做，不互相替代。

### 阶段 4：编译验证与按错迭代

**4.1 在 MounRiver Studio 中编译。** 把工程状态与编译意图说明清楚即可，由 MRS 侧执行编译，
不需要手写命令行构建。拿到的编译结果作为下一轮修改的输入。

按 `references/05_migration-rules.md` 第六节的四轮顺序推进：
预处理/语法错误 → 类型与成员错误 → 链接错误 → 行为核对。
每轮只修当前轮次的错误类型，改完重新编译，**不要跨轮次批量改**。

**4.2 判定**：

| 编译结果 | 处理 |
|---|---|
| 有错误 | 按轮次归类修复，回到 4.1 |
| 零错误、有告警 | 记录告警，**不要为消除告警改代码**（多为未使用变量/隐式声明） |
| 零错误零告警 | 进入 4.3 —— 这只是**编译通过**，不等于移植完成 |

**4.3 编译通过不等于移植完成。** 下列核对项编译期无法发现，必须逐项过：
**主频是否与源工程一致（按 HCLK / `SystemCoreClock` 对齐）**（见「主频与时钟配置专项」：
`SYSCLK_FREQ_*` 档位与 AHB 分频是否配对、`SystemCoreClockUpdate()` 是否已调用、
带 USB 时主频是否落在 48/96/144 MHz）、
波特率、中断优先级、I2C/SPI 时序、低功耗、
**Flash 页擦除是否已按 FLASH 专项改成 Fast**（`FLASH_ErasePage` 两侧**同名同签名**，
编译器一句提示都没有，漏改就是静默擦错范围 —— 这是本阶段**优先级最高**的一项），
**延时是否已按 ST 原形态分流改对**（见「延时与 SysTick 专项」：**空循环型** → `__NOP()` 忙等、
**不占 SysTick**、系数须按上下文给初值并**上机实测标定**；**SysTick / 滴答定时器型** → CH32 的
`Delay_Us` / `Delay_Ms`，其单位是 **10 ms**、换算须 **×10**，且 `EVT/EXAM/SRC/Debug/debug.c`
已加入工程、`Delay_Init()` 在 `SystemCoreClockUpdate()` **之后**调用
—— 三者同为「比对表与编译器都不覆盖」的项）、
**浮点格式化输出是否已按「printf 与浮点打印专项」处理**（原工程用了 `%f` / `%e` / `%g` 等浮点格式时，
MRS 工程的浮点打印默认**关闭** —— **编译与链接均不报错、运行期该浮点项不打印**，
须请 MRS 侧开启链接器选项 `Use wchprintfloat(-lprintfloat)`；无浮点输出则保持关闭，
该选项会拉进浮点 printf 引擎、显著增大体积 —— 同为「编译器不覆盖」的项），
**已用符号功能一致性复核是否已完成**（见同名专项：对用户代码实际用到的**外设库函数**
逐一核对两侧行为语义，有官方基线处不一致须补实现、无基线处须出清单待人工确认；
并确认库文件的增删已按官方 SPL 白名单甄别 —— 本项要读 `.mrs/originalKeilFiles/`，
**必须在阶段 4.4 删除该目录之前做完**）、
以及阶段 3B（裸地址/位带）与 3C（函数实现层）列出的差异。
**工程含 USB / HID 时，追加 `references/10_usb-migration.md` 的专项核对。**
USB 按**分层替换**处理（该文件 §1.3，方案 B）：**驱动层与配置层整份用 CH32 官方版，
业务层（`usb_desc` / `usb_prop` / `usb_endp` / 例程主文件）保留 ST 原样**，
编译报错就按代码逻辑改业务层的调用。
⚠ **「编译通过」不构成 USB 这块做完的证据** —— 该文件 §1.5 有 5 处编译器抓不到的静默失败点
（`DEVICE_PROP` 成员错位、`IMR_MSK` 条件编译门、`Ep0RxBlks`、`Init()` 全清、中断属性），
必须逐条自查；业务层改完还要按 §1.6 确认上位机侧零改动。
最终验收只能上真实硬件。

### 阶段 4.4：交付收尾 —— 删除 ST 源码副本目录（必做）

**顺序不可换。**

1. **先确认两件事已做完**：4.3 全部核对项已过完；
   「已用符号功能一致性复核专项」已出结论（🔴 已补实现并登记、🟠 待确认清单已交用户）。

   删除前逐项校验：

   | 校验项 | 要求 |
   |---|---|
   | 路径形态 | 必须是**当前新工程根**下的 `.mrs/originalKeilFiles`，**顶层目录名逐字匹配** |
   | 删除范围 | **只删这一层目录**；`.mrs/` 下的其它内容与工程其余部分一概不动。⚠ **工程里保留的 ST 库源文件不在删除范围内**（见「适用前提」第 1 条的两个对象） |

3. **交付说明里写明两点**：① 该副本目录已删除；② 本次复核用到的 ST 侧锚点（`文件:行号`）已随说明列出
   —— 删除后若仍需回查 ST 源码，重新执行工程级转换会再次生成该目录。

⚠ 这一步**不是可选清理**：早于第 1 步删除 = 直接丢掉复核能力（见硬约束）；

## 已经确认的结论

可以直接引用，不必重新推导：

- **函数 API 零签名冲突**：403 个原型中没有任何一个同名函数的返回类型或形参类型发生冲突，
  差异仅是形参命名（`GPIO_TypeDef*` 与 `GPIO_TypeDef *`），调用点无需改动。
- **初始化结构体基本一致**：19 个中 18 个完全相同，只有 ADC 多出两个成员（未赋值即为 0，不影响旧代码）。
- **参数校验层被整体移除**：STM32 的 264 个 `IS_*` 宏在 CH32 侧一个都没有。
- **寄存器名全部重编码**：1771 项位定义异名同值、22 个寄存器结构体成员几乎全改；
  CH32 对部分外设采用**扁平位命名**（`TIM_CEN` 而非 `TIM_CTLR1_CEN`），不能靠结构体成员名推导位宏名。
- **CH32 保留了向后兼容别名**：`GPIO_Remap_PD01`、`USART_IT_ORE`、`RCC_AHBPeriph_OTG_FS`、
  `PWR_PVDLevel_2V2..2V9`、CAN 的 `CANTXOK` 系列等旧名均可直接编译，**不需要为兼容而改名**。
- **中断处理函数名与 STM32 同名**，启动文件用 `.weak`，未实现的中断不会导致链接失败；
  但**中断编号体系不同**，任何裸数字写法必须改成符号。
- **CH32 无对应外设**：`DAC` / `CEC` / `FSMC` / `SDIO`，以及 `DMA2` / `ADC3` / `SPI3` /
  `CAN2` / `UART5`；定时器只有 `TIM1`~`TIM5`，STM32 的 `TIM6`/`TIM7`/`TIM8`/`TIM9`~`TIM17`
  全部不存在（注意 `ADC2`、`UART4`、`TIM5` 在 CH32V20x 上是**有**的，不要误判）。
- **TIM5 是 D8/D8W 才有的 32 位定时器**，需专用初始化结构体；D6 型号不可用。
- **裸地址可以直接沿用**：两侧外设基址常量完全相同，寄存器偏移在 19 个结构体中
  17 个完全一致，另 2 个（`SPI` / `FLASH`）只在尾部多一个或少一个寄存器，
  共有寄存器无一错位。这是本次比对中少见的「好消息」。
- **位带在 CH32 上完全没有对应物**：CH32 是 RISC-V，无位带硬件，
  `PERIPH_BB_BASE` / `SRAM_BB_BASE` 这两个宏在 CH32 侧完全不存在。
  凡是用到位带的代码，**多数会因缺少 `PERIPH_BB_BASE` 而编译报错**，
  例外是写成字面别名地址的那些 —— 那些编译器发现不了，只能靠扫描。
  改写方向：`BSHR`/`BCR` 或读-改-写。
- **`BSHR` 不是 `BSRR`**：CH32 的 `BSHR` 只置位、`BCR` 只清零，是两个寄存器分工；
  STM32 的 `BSRR` 一个寄存器兼顾「低 16 置位 / 高 16 清零」。
  `BSRR = (1 << (n+16))` 这类清零写法必须换成 `BCR`，改名字不够。
- **DBGMCU 不是内存映射**：CH32V20x 的调试停机控制是 RISC-V CSR(0x7C0)，
  STM32 的 `DBGMCU_BASE`（`0xE0042000`）在 CH32 上无效；芯片 ID 在 `0x1FFFF704`。
  且 `DBGMCU_Config(x, ENABLE)` 是整体覆写——多次分开调用会互相清除，需合并为一次 `A|B|C` 调用。
- **GPIOC 的引脚重编号不是「调用方无感」**：CH32 在 10 个 gpio 库函数里插了 GPIOC 重编号块，
  但开关 `MCU_Version` 是**文件级全局、只在 `GPIO_Init()` 内赋值一次**，其余函数只读不写 ——
  重编号**依赖调用顺序**，且**裸地址 / 位带直访 GPIOC 完全不参与**。
  `MCU_Version` 未在任何头文件暴露（无 `extern`），用户代码查不到。
  触发条件为 `CH32V20x_D6` 且 `(*(uint32_t*)0x40022030 & 0x0F000000) == 0`（旧版芯片）。
  gpio 的 14 条实现层差异里有 12 条是它。详见 `references/08_func-behavior.md` 第三节第 1 条。
- **`SPI_StructInit` 少初始化一个成员**：STM32 写 9 个、CH32 只写 8 个，
  **`SPI_NSS` 不被赋值** → 该成员残留栈值。这是「函数体差异」里最隐蔽的一条，
  因为调用写法完全没变。详见 `references/08_func-behavior.md` 第三节第 2 条。

### FLASH 专项（已逐源码核实，是本次比对中陷阱最多的模块）

- **`FLASH->ACR` 在 CH32 侧是另一个寄存器**：同偏移 `0x00` 处 CH32 叫 `FLASH->ACTLR`，
  但**一条位定义都没有**，与 STM32 的 `ACR`（`LATENCY`/`HLFCYA`/`PRFTBE`/`PRFTBS`，7 条位定义）
  毫无关系。等待周期与指令预测搬到了**内核 CSR `0xBC0`**，由启动文件写入并默认全开
  （`SRC/Startup/startup_ch32v20x_D6.S` 写 `0x1F`）。
  因此 `FLASH_SetLatency` / `FLASH_HalfCycleAccessCmd` / `FLASH_PrefetchBufferCmd` /
  `FLASH_GetPrefetchBufferStatus` **四个函数在 CH32 侧不存在，必须整句删除**；
  也不能再依赖「运行中动态开关预取」的用法 —— CH32 侧预取是启动即开、用户代码关不掉。
  替代能力：Flash 访问时钟用 `FLASH_Access_Clock_Cfg(FLASH_Access_SYSTEM | FLASH_Access_SYSTEM_HALF)`，
  它写的是 `FLASH->CTLR` bit25，**调用前必须先 `FLASH_Unlock()`**。
- **寄存器改名（同偏移）**：`ACR`↔`ACTLR`、`OPTKEYR`↔`OBKEYR`、`SR`↔`STATR`、`CR`↔`CTLR`、
  `AR`↔`ADDR`、`WRPR`↔`WPR`；选项字节结构体 `OB_TypeDef` 里 `RDP`↔`RDPR`、`WRP0..3`↔`WRPR0..3`。
  CH32 的 `FLASH_TypeDef` 在尾部**多一个 `MODEKEYR`（`0x24`）**，`0x00`~`0x20` 共有寄存器无一错位。
- **`FLASH_GetStatus()` / `FLASH_GetBank1Status()` 删掉了编程错误档**：CH32 只判
  BSY → WRPRTERR → COMPLETE，**永远不会返回 `FLASH_ERROR_PG`**（库头也没有
  `FLASH_FLAG_PGERR` / `FLASH_FLAG_BANK1_PGERR` 这两个标志宏）。
  上层的 `FLASH_WaitForLastOperation()` 只关心「忙 / 超时」，不受影响；
  但**把 `FLASH_ERROR_PG` 当成一种「一定会出现」的状态去处理的用户代码会失效**。
- **`FLASH_FLAG_OPTERR` 取值不同**：STM32 `0x00000001`，CH32 `0x80000001`。
  用宏名比较（`FLASH_GetFlagStatus(FLASH_FLAG_OPTERR)`）结果正确，
  但**把宏值当 OBR 掩码用会出错** —— CH32 源码自己就改写成
  `FLASH->OBR & (1<<0)`。凡是出现 `x & FLASH_FLAG_*` 的写法都要核。
- **写保护粒度不同，照搬宏名会静默扩大保护范围**：STM32 按页（67 条，含三种容量分档），
  CH32 只按 4 KB sector（33 条）。只有大容量档的
  `FLASH_WRProt_Pages4n..4n+3` ↔ `FLASH_WRProt_Sectors n` 能一一对应；
  中容量档 `FLASH_WRProt_Pages0to1`（覆盖 2 KB）落到 `Sectors0`（覆盖 4 KB）会**多保护 2 KB**。
  两侧 `FLASH_WRProt_AllPages` ↔ `FLASH_WRProt_AllSectors` 是唯一同值对（`0xFFFFFFFF`）。
- **选项字节写法和 STM32 不同**：STM32 直接写 `OB->WRP0..3` / `OB->RDP` / `OB->USER`
  并靠 `FLASH_WaitForLastOperation()` 轮询超时；CH32 改成 `for` 循环往
  `0x1FFFF800 + 2*i` 逐半字写，内部 `while(FLASH->STATR & SR_BSY);` 死等，
  整体擦除后还要追加 `FLASH_EraseAll_Delay()` 延时。
  **用户代码不要自己重写选项字节流程，一律走库函数**。
- **`FLASH_Status` 前 5 项同值，CH32 多 3 项**：`FLASH_OP_RANGE_ERROR`(253)、
  `FLASH_ALIGN_ERROR`(254)、`FLASH_ADR_RANGE_ERROR`(255)，只由 CH32 独有的
  `FLASH_ROM_ERASE()` / `FLASH_ROM_WRITE()` 返回。
  另外**两侧都不能把返回值的 0 当成功**（`FLASH_COMPLETE` 是 4）。
- **CH32 侧 `FLASH_EraseAllPages()` / `FLASH_EraseAllBank1Pages()` 结束后有额外延时**，
  `FLASH_EraseAll_Delay(150000)`（D6）/`(180000)`（D8/D8W）——
  这是 CH32 的擦除等待要求，**不要为了「和 STM32 一致」把它删掉**。
- **🔴 页擦除一律改 Fast（256 B × 4）—— 这是迁移的必需修复，不是可选优化。**
  两侧 `FLASH_ErasePage` 都**不对传入地址做对齐**：STM32 擦「该地址所属的 1 KB 页」，
  CH32 擦「该地址所属的 4 KB sector」。沿用在 STM32 上按 1 KB 页推算出来的地址，
  在 CH32 上必然擦错范围 —— 轻则数据跨 sector、写进未擦区**静默失败**，
  重则擦掉同 sector 前半段的**用户代码**（`0x0800FC00` 这类「1 KB 页首」地址在 CH32 上
  只是 4 KB sector 的中段，其前半段正是代码区）。
  统一改法（`256 B × 4 = 1 KB`，粒度与 STM32 精确等价，**地址一个字都不用动**）：
  ```c
  uint32_t base = PageAddress & ~((uint32_t)0x3FF);   /* ① 必须向下对齐到 1 KB 页首 */
  FLASH_Unlock_Fast();                                 /* ② 必须换 Fast 解锁 */
  for (i = 0; i < 4; i++)
      FLASH_ErasePage_Fast(base + i * 256);            /* ③ 必须循环 4 次 */
  FLASH_Lock_Fast();
  ```
  三个必须做对的点（漏掉任一都**静默出错**）：
  - **① 对齐方向是「向下」**：WCH 官方的 `CFG_ERASE(addr, len)`
    （`EVT/EXAM/ETH/ETH_CFG/ModCfg/ModuleConfig.c:23`）是**区间语义**「擦 `[addr, addr+len)`」，
    照搬它的循环会**向右越界到相邻页**；而 `FLASH_ErasePage` 是「擦 addr 所在那一页」的语义，
    起点必须 `& ~0x3FF`。
  - **② 必须换解锁函数**：`CR_PAGE_ER`(bit17) 要 `MODEKEYR` 那把锁，只调 `FLASH_Unlock()`（仅 `KEYR`）
    会**擦不掉、且不报错**。它与普通擦的 `CR_PER_Set`(bit1) 是**同寄存器不同位**，互不干扰。
  - **③ 编程侧一格不动**：`FLASH_ProgramHalfWord` / `FLASH_ProgramWord` 仍走
    `FLASH_Unlock()` / `FLASH_Lock()`，两套锁**分段不交叉**（官方 `IAP_EEPROM_WRITE` 即此写法，
    `EVT/EXAM/ETH/ETH_IAP/User/IAP_Task.c:70`）。
  官方同款范式：`ModuleConfig.c:23` 的 `CFG_ERASE` 与 `IAP_Task.c:46` 的 `IAP_EEPROM_ERASE`
  （两者**逐字相同**），都是「Fast 解锁 → 循环 `FLASH_ErasePage_Fast` → Fast 上锁」。
  ⚠ 两个遗留代价：`FLASH_ErasePage_Fast` 返回 `void`、内部 `while(FLASH->STATR & SR_BSY);` 死等
  → **失去擦除失败检测**（普通 `FLASH_ErasePage` 有 `FLASH_Status`）；`FLASH_Lock_Fast()` 只关
  `CR_FLOCK`(bit15)，普通锁 `CR_LOCK`(bit7) 仍开着（官方 `CFG_ERASE` 也没补，要补就
  `FLASH->CTLR |= CR_LOCK_Set;`）。擦除成功后读回是 `0xe339e339` 而非 `0xFFFFFFFF`，**不是故障**。
  ⚠ **只保留一条判断**：地址范围是否**越界**（Fast 救不了越界，如 32 KB 档去访问 `0x0800FC00`）。
  ⚠ **排查入口**：「**注释改了、代码没改**」是这类问题的典型信号 —— 本次即 `MyFLASH.h` 注释
  从 1k 改成 4k 而 `Store.c` 的地址与 `STORE_COUNT` 一字未动。

### 主频与时钟配置专项（FLASH、延时之后的第三条硬性修复）

- **规则：迁移后工程的主频必须与原工程一致。** 口径是 **HCLK（即 `SystemCoreClock`）**，不是 `SYSCLK` ——
  CH32 的 `SystemCoreClockUpdate()`（`system_ch32v20x.c:130-205`）末尾会做
  `SystemCoreClock >>= AHBPrescTable[HPRE]`，`RCC_GetClocksFreq()`（`ch32v20x_rcc.c:552-636`）同样是
  `HCLK = SYSCLK >> presc`。**判定「一致 / 不一致」之前，先确认比的是 HCLK 还是 SYSCLK，
  不要拿 SYSCLK 的 144 与 HCLK 的 72 去误判。**

- **推荐做法（源工程选 72 MHz 时）**：CH32 侧选 `SYSCLK_FREQ_144MHz_HSE` 档，在 `main()` 起始加一句：
  ```c
  RCC->CFGR0 |= (uint32_t)RCC_HPRE_DIV2;   /* PLL = 144M，AHB 二分频 */
  SystemCoreClockUpdate();                 /* ⚠ 必须手动调，见下 */
  ```
  结果 **HCLK = 72 MHz / PCLK2 = 72 MHz / PCLK1 = 36 MHz**，与原 ST 工程**逐项相同、零参数重算**；
  USB 也能取到 `144 / 3 = 48 MHz`。这是 WCH 官方手法（先例：D8W 的 120 MHz 档
  `EVT/EXAM/**/system_ch32v20x.c:628-631`，PLL 输出 240 MHz + `RCC_HPRE_DIV2` → HCLK 120 MHz）。
  - ⚠ **`SystemInit()` 不调用 `SystemCoreClockUpdate()`**（`system_ch32v20x.c:111-120` 只调
    `SetSysClock()`）→ `SystemCoreClock` 在 `main` 之前仍是**编译期宏值**，
    **必须在它被使用之前（`Delay_Init()` / 波特率计算之前）显式调一次**，否则基准全错。
  - ⚠ 寄存器名是 `RCC->CFGR0`（CH32）而非 STM32 的 `RCC->CFGR`；`RCC_HPRE_DIV2` 编码 `0x80`，
    `AHBPrescTable` 索引 8 → ÷2，能被 `SystemCoreClockUpdate()` 正确折算。

- **源工程是其它主频时**：CH32 也选与之相同的 `SYSCLK_FREQ_*` 档；**CH32 没有对应档位**（例如 24 MHz）时，
  两种做法二选一：
  1. **官方结构法（推荐）** —— 直接在 `system_ch32v20x.c` 里照 WCH 的写法加档位宏 + 分支，
     `SystemInit()` 自动生效，配置不散落在用户 `main` 里。
  2. **显式调用法** —— 手工生成 `SetSysClockToXX_HSE()`，在 `main` 里
     `RCC_DeInit(); SetSysClockToXX_HSE(); SystemCoreClockUpdate();`。
     `RCC_DeInit()` 存在于 `ch32v20x_rcc.c:82`。
     ⚠ **抄现成档位改系数时，注释里的主频要一起改**：24 MHz = `HSE(8M) × 3`（`RCC_PLLMULL3`），
     从 48 MHz 档抄来若留着「`PLLCLK = HSE * 3 = 48 MHz`」的注释就是**错的**（实为 24 MHz），
     系数对、注释错，会误导后来人。

- **🔴 带 USB 时的主频约束**：`RCC_USBCLKConfig` 只写 `CFGR0` bit22-23，**没有 Div1.5**；
  CH32 官方 `Set_USBConfig()`（USB 例程 `USBLIB/CONFIG/hw_config.c:57`）**只覆盖
  144→Div3 / 96→Div2 / 48→Div1** 三分支，判据是 `SYSCLK_Frequency`。
  → **带 USB 时 SYSCLK 只能取 48 / 96 / 144 MHz**。若为了「对齐 72 MHz」改用
  `SYSCLK_FREQ_72MHz_HSE` 档，`SYSCLK = 72M` 三分支**全不匹配 → USB 时钟分频不被配置 → USB 静默失效**。
  **正解仍是「144 MHz 档 + HPRE÷2」**：SYSCLK 保持 144 MHz（USB 拿 48 MHz），HCLK 才落到 72 MHz。
  详见 `references/10_usb-migration.md`。

- **EVT 默认档是 `SYSCLK_FREQ_96MHz_HSE`**（`system_ch32v20x.c:25`，旁边 72M 那行是注释），
  不是 72 MHz —— 迁移时必须**显式确认档位，不要沿用 EVT 默认**。

- ⚠ **主频一致属「编译期零提示」项**：档位宏选错、忘了 `SystemCoreClockUpdate()`、HPRE 忘了配，
  编译器一句都不会说，只能靠上机打印 `SystemCoreClock` 验证。

### 延时与 SysTick 专项（ST 侧延时全在用户代码里，比对表与编译器都不覆盖）

- **ST SPL 库里没有任何 Delay 函数** —— 全库扫下来只命中 `stm32f10x_flash.c:84`
  一句 `/* Delay definition */`（空注释，其后并没有函数体），
  延时实际全部定义在用户代码或例程公共文件里，**差异比对表里不会出现**，
  编译器也一句提示都没有。实测有三种形态：

| 形态 | 典型签名 | 参数语义 | 实测出处（`stm32f10x-stdperiph-lib-master`） |
|---|---|---|---|
| A1 无参空循环 | `void Delay(void)` | 固定 `0xFFF` 次循环 | `Project/STM32F10x_StdPeriph_Examples/CAN/DualCAN/main.c:379` |
| A2 带参空循环 | `void Delay(__IO uint32_t nCount)` | **循环次数**（不是时间） | 同上 `CRC/CRC_Calculation/main.c:99` |
| B SysTick 递减 | `void Delay(__IO uint32_t nTime)` | **10 ms**（不是 1 ms） | 同上 `FLASH/Dual_Boot/main.c:252` |

- **路线 ② 的目标函数在 `EVT/EXAM/SRC/Debug/debug.c`**：
  `Delay_Init()` / `Delay_Us(uint32_t n)` / `Delay_Ms(uint32_t n)`。
  - ⚠ **`Debug/` 是 EVT 例程的公共源码目录，不是外设驱动库**（库在 `SRC/Peripheral/`）。
    迁移时必须把它**一并加进工程**（连同 `debug.h`），否则 `Delay_*` 直接未定义、链接期才报错。
  - ⚠ **调用顺序不能颠倒**：`SystemCoreClockUpdate()` → `Delay_Init()`。
    `Delay_Init()` 内部按 `SystemCoreClock / 8000000` 算步长（`debug.c:29-33`），主频没更新就先调它，
    **整个延时基准全错**（这也是 `HSE_VALUE` 必须按实际晶振确认的原因之一，见 `05_migration-rules.md` 3.2）。
  - ⚠ `Delay_Us` / `Delay_Ms` 是**轮询实现**（先写 `SysTick->CMP`，再 `while` 等 `SysTick->SR` 置位），
    **不占用 SysTick 中断**，因此整段换成它之后通常**不再需要 `SysTick_Handler`**。

- **🔴 改法 = 按 ST 原形态分流，两条路线不要混 —— 这是本专项的核心。**
  这么做的原因：CH32 侧 `debug.c` 的 `Delay_*` **占用 SysTick**，若拿它无差别替换所有延时，
  会与源工程已有的 SysTick 用途（时基 / OS 节拍）冲突。**按原形态分流即可避开：
  源工程只用空循环延时的，迁移后仍然不碰 SysTick。**

  **路线 ①：形态 A（空循环）→ 改用 `__NOP()` 忙等，不占 SysTick。**
  ST 侧空循环的参数是「循环次数」，在 RISC-V 上实耗周期完全不同、**没有时间语义**，
  改写成按 `SystemCoreClock` 折算的 `__NOP()` 忙等：
  ```c
  void delay_ms(int time)
  {
      int i = 0;
      while (time--)
      {
          i = SystemCoreClock / 1000 / 8;     /* ⚠ 系数是经验值，须上机标定 */
          while (i--) { __NOP(); }
      }
  }
  void delay_us(int time)
  {
      int i = 0;
      while (time--)
      {
          i = SystemCoreClock / 1000000 / 10; /* ⚠ 与 ms 版系数不一致，见下 */
          while (i--) { __NOP(); }
      }
  }
  ```
  调用点由「循环次数」改为「毫秒 / 微秒数」—— **原参数没有时间语义，不能机械换算**，
  按上下文各给一个合理值（例如原 `Delay(0xFFF)` 用于「等 LED 人眼可见」，取 `delay_ms(150)`），
  **代码里注明「周期待实测」，定量交给上机**。
  - ✅ `__NOP()` 在 CH32 侧存在（`SRC/Core/core_riscv.h:155-157`，`__asm volatile("nop")`），
    循环体含 volatile asm，**不会被编译器优化删掉**。
  - 🔴 **`/8`、`/10` 系数与编译优化等级强耦合**：MRS 工程默认 **`-Os`**（`.cproject` 的
    `optimization.level`），换成 `-O0/-O1/-O2` 后每圈指令数就变、系数即失效。
    **必须上机实测标定**，不要当精确值用。
  - 🔴 **`/8`（ms）与 `/10`（us）互相矛盾**：同一内层循环 `while(i--){__NOP();}` 每圈周期数
    只能是**一个值**，两版隐含值不同 → **至少一个不准，两处都要实测**。
    附带：72 MHz 下 `SystemCoreClock/1000000/10` = 7（取整），us 级固有误差约 −3%；
    若 `SystemCoreClock ≤ 8 MHz`，us 系数取 0，`delay_us` **完全失效**。
  - ⚠ `time` 类型：ST 原版多为 `u16`（无符号），本公式用 `int`（有符号）——
    负数入参会退化成超长循环。
  - ⚠ 这是**自研手法、非官方范式**（EVT 里 `__NOP()` 只出现在 BLE/RF 时序等待，
    没有一处是通用 ms/us 延时）。官方通用延时范式是路线 ②。
  - **不要**为了「保持原样」去凑一个等价的空循环 —— 那等于把不确定的时序原封不动搬过去，
    在新平台上照样不准，还失去了函数名与参数的可读性、可调性。

  **路线 ②：形态 B（SysTick / 滴答定时器）→ 改用 CH32 的 `Delay_Init` / `Delay_Us` / `Delay_Ms`。**
  ST 侧参数有明确时间语义、但**单位是 10 ms**（例程配置 `SysTick_Config(RCC_Clocks.HCLK_Frequency / 100)`，
  `FLASH/Dual_Boot/main.c:113` → 每 10 ms 中断一次），所以 `Delay(5)` 表示 **50 ms**：
  ```c
  Delay_Ms(nTime * 10);   /* ST 侧单位是 10 ms —— 漏乘 10 就是延时缩短十倍 */
  ```
  同时**整段删除**原 SysTick 相关代码：`SysTick_Config(...)`、`TimingDelay` 变量、
  `TimingDelay_Decrement()`、`SysTick_Handler()` —— 之所以能删，是因为原工程把 SysTick **只**用于延时；
  若还兼作其它用途，见下方互斥说明。改完后 SysTick 归 `debug.c` 的轮询逻辑使用。
  - ✅ 该路线的优点是**精度与优化等级无关**（靠硬件计数），这是它与路线 ① 的本质区别。

- **🔴 与 `references/05_migration-rules.md` 第 3.1 节的 `SysTick_CLKSourceConfig` 条目互斥，必须二选一。**
  该条原要求「不要直接删掉调用，补一个等价实现（写 `CTLR` 对应位）」——
  这只在**用户自己用 SysTick** 时成立。
  - 走**路线 ②（`Delay_*`）**：SysTick 由 `debug.c` 全权接管（它每次调用都会改写 `CTLR`），
    用户的 `SysTick_CLKSourceConfig` 应**直接删除、不要再补实现**；两处都配 SysTick 会互相踩。
    仅当用户**另有**基于 SysTick 的独立功能（跑表、OS 节拍、自建时基）时，才保留自配逻辑，
    此时**不要**再调 `Delay_*`。
  - 走**路线 ①（`__NOP` 忙等）**：完全不动 SysTick，用户的 SysTick 配置（若有）按原意保留、各自处理。

- **CH 侧 `SysTick` 结构体只有四个成员，且没有任何位定义宏**
  （`core_riscv.h`：`CTLR` / `SR` / `CNT` / `CMP`，基址 `0xE000F000`）。
  要写位只能查手册对着写位号 —— `debug.c` 用到的是 bit4 / bit5 / bit0，
  `EXAM/INT/Interrupt_VTF/User/main.c` 用的是 `SysTick->CTLR = 0x7`（中断模式）。
  **不要照抄 ST 的宏值**；位定义语义以 `CH32FV2x_V3xRM` 为准，`debug.c` 的实际用法
  **不构成语义依据**（它是实现，不是规格）。
- `SysTick_Handler` 在 CH 侧**是存在的**（`EXAM/APPLICATION/Electric_Hair_Dryer/User/M6_SpeedLoop.c:15`、
  `EXAM/INT/Interrupt_VTF/User/main.c:26`），带 `__attribute__((interrupt("WCH-Interrupt-fast")))`。
  **不存在的只是库函数 `SysTick_Config`**。

### printf 与浮点打印专项（工具链配置类，第四条同类硬性修复）

- **症状**：原工程用了 `printf("%f", x)` 这类**浮点格式化输出**，迁移后在 MRS 里编译、链接**都不报错**，
  但运行期该浮点项**不打印**。这又是一条「比对表与编译器都不覆盖」的项。
- **机制**：MRS（GCC 工具链）的浮点 printf 由**链接器选项**控制 ——

  `ilg.gnumcueclipse.managedbuild.cross.riscv.option.c.linker.printfloat`，另有 C++ 版）。

  其余根本不设置 —— 取工具链默认 = **关**。
- **铁证（此项 = `true` 且真用 `%f`）**：`EXAM/TIM/Encoder/.cproject:86` `value="true"`
  ↔ `TIM/Encoder/User/main.c:189` `printf("Encoder speed= %f\r\n", …)`；
  另有 `EXAM/APPLICATION/USBPD/I2C_OP_CH223/User/main.c:223` 用 `%0.1f`。
- **检测（对「原工程」= 用户代码 + 库 执行）**：
  ```bash
  grep -rnE '(printf|fprintf|sprintf|snprintf|vprintf|vsnprintf|puts)\s*\(' \
       --include='*.c' --include='*.h' . | grep -E '%[-+ #0-9.*]*[fFeEgGaA]'
  ```
  - ⚠ **自定义封装要回溯**：`LOG(...)` / `ee_printf` / `DBG(...)` 这类宏或包装函数，
    不能只看格式串，必须追到最终的 printf 实现。
  - ⚠ **输入侧不算**：`scanf` / `sscanf` 的 `%f` 是**输入**转换、另有开关（本次未核实），不要混处理。
- **处理动作 —— 通知 MRS 内智能体，不要自己改工程属性文件。** 命中即用自然语言让 MRS 侧开启，

  > 本工程使用了 printf 浮点格式（`%f` / `%0.1f` 等），请为本工程开启浮点打印支持：
  > 打开链接器选项 `Use wchprintfloat(-lprintfloat)`（默认关闭）。

  **不要**去解析或修改 `.cproject` / `.uvprojx` —— 与「型号宏交 MRS 侧、不改工程属性文件」同一条原则。
- **不要无脑开启**：该选项会把整套浮点 printf 引擎链进来、**显著增大代码体积**。

### 已用符号功能一致性复核专项（交付前最后一道关）

- **为什么需要**：本技能的全部结论按**官方 SPL V3.5.0** 建立，而用户工程里的 ST 库是**另一份拷贝**。
  库一旦被本地改过（换版本 / 改 `.h` 宏值 / 改 `.c` 函数体 / 增删库文件），相关结论即失效 ——
  **版本宏判不出本地改动**（改函数体、改宏值都不动它）。
  更关键的是：**用户改过的那段逻辑本身也是要迁移的代码**，不检出就是**功能丢失**。
- **范围（只做这一层，不要扩大）**：用户代码**实际用到的、属于外设库的**函数与宏。
  **用户层自己写的函数不需要** —— 它是「被转换的对象」，没有原版基线可比；没用到的库函数也不核。

#### 一、🔴 参照物只有一个是安全的

**判据 = 「用户 ST 库的实际实现」↔「本技能记录的 ST 侧基线」，不是「CH32 库代码」。**

| 参照物 | 后果 |
|---|---|
| ❌ **CH32 库实际代码** | CH32 剔了 `assert_param`、改了寄存器名/宏名、位带改成读-改-写 → 两侧原始代码**必然大片不同** → 假阳性海量 → 会把**几百个本来正确**的函数重写一遍 |
| ✅ **`08_func-behavior.md` 记录的 ST 侧锚点**（`ST 行号` + 差异摘要） | 差异是**官方固有**、已被记录，不与「用户改动」混淆 |

**硬约束**：内容对照**只在「用到的库函数 ∩ `08` 那 76 条」上判**。
其余用到的库函数**没有 ST 侧基线** —— `08:24` 那句「未出现在本表的函数归一化后完全一致」
是**构建期**归一化的结论，**运行期无法复现** → **禁止据此下判定**，只能走梯次 C。

#### 二、执行梯次（成本递增，前一层能定性就不进下一层）

| 梯次 | 对象 | 动作 | 成本 |
|---|---|---|---|
| **A 查表** | 用到的符号 ∩ `08` 76 条 / `03` §一 22 条异值 / `03` §五 25 条仅 ST 存在 / `01_regmap` | 结论现成，直接落 | ≈0 |
| **B 宏值核对** | 用到的**宏** | 读 **`.mrs/originalKeilFiles/`** 里用户 ST 头文件的**实际值** ↔ `01_regmap` / `03` §一 记录的 ST 侧值 → 不同即该头被改过 | 低（各 grep 一次） |
| **C 源码对照** | 只核「**不在任何表里**」且**用到的**库函数 | 读 **`.mrs/originalKeilFiles/`** 的 ST 侧函数体 ↔ 目标工程 CH32 侧函数体，按 `08` 的判定口径做语义等价判断 | 高，但数量应不多 |

> 🔴 **本专项必须在删除 `.mrs/originalKeilFiles/` 之前完成** —— 它是全流程里**唯一**需要 ST 库源码的
> 交付前环节，也是「用户改过 ST 库」这整类风险的**唯一**检出手段。删除时机见阶段 4.4。

#### 三、判定与处置

| 判定 | 含义 | 动作 |
|---|---|---|
| 🟢 一致 | 与基线相符 | 不动 |
| 🟡 等价 | 两侧不同但语义等价（仅 `assert_param` / 仅命名 / 仅类型转换 / 位带改写） | **不动** —— 这是官方固有，不是用户改的 |
| 🔴 **不一致** | **有基线**且实际实现与之不符 ⇒ 库被改过 | **补回该逻辑**（见下条护栏），并逐条登记 |
| 🟠 **无基线** | 用到的库函数不在任何表里，两侧语义无法自动判定 | **只报告**，列入「待人工确认清单」，**不擅自补** |

> 补实现**不是**「照抄 ST 代码」：CH32 侧的目标是**在原位置恢复该语义**，用 CH32 的 API 表达。

#### 四、补实现四条护栏（仅 🔴 适用）

1. **优先用 CH32 自有 API 组合**实现，**不手写寄存器**（否则丢掉库里的边界处理与时序）。
2. **最小改动**，能加在用户层就不动 CH32 库。
3. 必须标注：`/* [迁移补丁] 原 ST 侧行为：… 依据：<08 行号 / 用户代码位置> */`。
4. 逐条写进交付说明，**不得静默**。

#### 五、库文件「增 / 删 / 改」全覆盖

| 操作 | 形态 | 检出手段 |
|---|---|---|
| **改** | `.h` 宏值 | 梯次 B |
| **改** | `.h` 结构体成员 | 换头后编译报错 |
| **改** | `.c` 函数体（**增删行**） | 梯次 A：`08` 的 ST 行号锚点漂移 |
| **改** | `.c` 函数体（**等量替换**） | 梯次 C —— **唯一手段**，靠内容对照 |
| **删** | 删函数 / 删宏（被使用） | 链接 / 编译报错 |
| **增** | 库头新增宏 | 编译报错（宏不存在） |
| **增** | 库文件内新增函数 | 链接报错（库已移出）—— 但**不要顺手删掉调用**，按用户代码纳入迁移 |
| **增** | 库目录新增 `.c` / `.h` | ⚠ **不能靠 `stm32f10x_*.c` 通配移出** —— 须按**官方 SPL 白名单**甄别（`05` 第二节第 3 项）：白名单**外**的 = 用户新增，**不移出**，按用户代码迁移 |

> ⚠ **已知弱点，如实声明**：**等量替换**（只改数值、不增删行）只有梯次 C 能发现，判据依赖判断力。
> 因此**真机验证仍是最后一道网**，本专项不替代它。

## 硬约束

- **不要为了消除编译错误而自造兼容层。** 目标库不做参数校验，自行补上 `IS_*` 宏会造成与目标库行为不一致。
- **不要因为数值不同就修改代码。** 先查 `references/03_semantic-gaps.md` 的判定列；标为「兼容别名 / 库内自洽」的项保持原样。
- **不要臆造 CH32 侧的行为。** PVD 档位对应的实际电压阈值、低功耗位定义等属硬件规格，
  本次比对未覆盖，必须查 CH32 数据手册或实测，不可推断。（**Flash 页大小已核实**，
  不在此列：CH32 普通擦 = 4 KB sector、Fast 擦 = 256 B，见上文 FLASH 专项。）
- **Flash 的规则是「擦除改 Fast，编程不用 Fast」。** 页擦除按上文 FLASH 专项统一改成
  「向下对齐 1 KB + 4 × `FLASH_ErasePage_Fast`」—— **这是修复，不是可选优化**，
  因为 STM32 的 1 KB 页边界在 CH32 上必然擦错范围。
  但**不要**用 `FLASH_ProgramPage_Fast` 去替换 `FLASH_ProgramHalfWord` / `FLASH_ProgramWord`：
  它是 256 B **整页一次性提交**（凑满 64 字才置 `CR_PG_STRT`），**没有半字 / 字接口**，
  与逐半字写入的语义不对应，替换会逼你连带重写整个存储模块。
  `FLASH_Lock_Fast`（关 `CR_FLOCK`）与 `FLASH_Lock`（关 `CR_LOCK`）是**两把不同的锁**，
  必须**分段不交叉**地配对使用。
  **也不要把 `FLASH_ROM_ERASE` / `FLASH_ROM_WRITE` 当成 `FLASH_ErasePage` /
  `FLASH_ProgramWord` 的替代品** —— 它们按地址区间操作、会多做范围与对齐校验并返回
  3 个 STM32 没有的 `FLASH_Status` 值，语义不同。
- **迁移后工程的主频必须与原工程一致，口径是 HCLK（`SystemCoreClock`），不是 SYSCLK。**
  72 MHz 源工程的推荐做法：CH32 选 `SYSCLK_FREQ_144MHz_HSE` 档 +
  `RCC->CFGR0 |= RCC_HPRE_DIV2; SystemCoreClockUpdate();` → HCLK 仍 72 MHz，
  PCLK2 / PCLK1 与原工程相同、**零重算**。⚠ **`SystemInit()` 不调用 `SystemCoreClockUpdate()`**，
  改完时钟必须手动调一次（`Delay_Init()` 与波特率都依赖它）。
  ⚠ 带 USB 时主频受 **48 / 96 / 144 MHz** 约束（`RCC_USBCLKConfig` 无 Div1.5，
  官方 `Set_USBConfig()` 只覆盖三分支），改用 72 MHz 档会让 USB 分频不被配置而**静默失效**。
  详见「主频与时钟配置专项」。
- **延时类函数必须按 ST 原形态分流改，不要一律套 `Delay_*`、也不要保留原空循环。**
  ST SPL 库里**没有任何 Delay 函数**（延时全在用户代码里，比对表与编译器都不覆盖）。
  分流口径（见上文「延时与 SysTick 专项」）：
  - **空循环型（形态 A）→ `__NOP()` 忙等**，参数由「循环次数」改为「ms / us 数」；
    系数是经验值、**与 `-Os` 优化等级强耦合**，必须按上下文给初值 + **上机实测标定**。
    这条路线**不占 SysTick**，源工程本来不碰 SysTick 的，迁移后也不应引入。
  - **SysTick / 滴答定时器型（形态 B）→ CH32 的 `Delay_Init` / `Delay_Us` / `Delay_Ms`**，
    并整段删掉原 SysTick 代码。工程要补进 `EVT/EXAM/SRC/Debug/debug.c`（+ `debug.h`），
    并在 `SystemCoreClockUpdate()` **之后**调 `Delay_Init()`（顺序颠倒则整个延时基准错）。
    该形态单位是 **10 ms**（不是 1 ms），换算须 **×10**。
  ⚠ 与 `references/05_migration-rules.md` 3.1 节 `SysTick_CLKSourceConfig` 条目**互斥**：
  走形态 B 时 `debug.c` 全权接管 SysTick，原调用应**删除、不要再补实现**；
  走形态 A 时完全不动 SysTick。
- **不要因为偏移一致就跳过裸地址核对。** 「偏移一致」是本次针对 19 个标准外设结构体的结论，
  不覆盖用户自定义地址、外设实例指针运算、以及手册上与库定义不一致的地址。
- **不要在封装不匹配时自行改封装或建议换引脚。** V203 侧最大封装是 LQFP64M，
  **没有 LQFP100 / LQFP144**。按 `references/09_model-mapping.md` 第二节输出降级提示，交用户决策。
- **USB 按分层替换处理：不要整套换库，也不要逐文件重写。** 做法见
  `references/10_usb-migration.md` §1.3 —— **驱动层**（`USB-Driver/{inc,src}` 的 15 个文件）
  与**配置层**（`usb_conf.h`、`hw_config.c/h`、`usb_istr.c/h`、`usb_pwr.c/h`）**整份用 CH32 官方版**；
  **业务层**（`usb_desc.c/h`、`usb_prop.c/h`、`usb_endp.c`、例程主文件）**保留 ST 原样**，
  编译报错就按代码逻辑改业务层的调用。
  理由**不是**寄存器不兼容 —— 两侧 `RegBase`(`0x40005C00`) / `PMAAddr`(`0x40006000`) 与
  `CNTLR`/`ISTR`/`FNR`/`DADDR`/`BTABLE` 的偏移**完全相同**，位宏与函数名也一致，
  **只有寄存器指针宏 `CNTR`→`CNTLR` 改名**。照搬的理由是 CH32 侧多出的**行为**补丁
  （3 个端点状态宏的 `while` 读回校验、`_SetEPRxCount` 的 EP0 分支与 `Ep0RxBlks`、
  `USB_Istr()`/`Suspend()` 的复位重同步、`Init()` 里的「全清 + 口复位 + 20 ms」）
  **编译器一句都不会报**，逐行改反而容易漏。
  同一路径原地替换、或换目录都行，**但同名文件只能留一份**（两侧库文件名完全相同）。
- **USB 这块不要用「编译通过」判定做完。** 编译通过只说明接口对上了。业务层定稿后必须再过
  `references/10_usb-migration.md` §1.5 的 5 条自查：`DEVICE_PROP` 成员错位（CH32 多一个
  `RxEP_buffer`，ST 的 11 个初始化值会让 `MaxPacketSize` 变成 0 → 枚举失败，只有 warning）、
  `IMR_MSK` 条件编译门、`Ep0RxBlks`（只补变量定义不够）、`XXX_Init()` 缺 5 句、
  中断服务函数的中断属性。
- **业务层不要为「和 CH32 一样」而改名或改结构**，尤其 `usb_desc.c/h` ——
  它是上位机可见接口（VID/PID、接口/端点、报告描述符、字符串）的**全部来源**。
  改完按 §1.6 确认上位机侧零改动。
