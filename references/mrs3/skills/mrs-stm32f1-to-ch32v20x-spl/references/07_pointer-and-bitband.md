# 地址指针直访寄存器 与 位带操作

> 本文件覆盖两类「绕过外设库符号名、直接碰硬件地址」的写法。
> 它们的共同点是：**编译器不会报错**。改错名字编译器会拦，改错地址不会。
> 因此这两类必须人工核对，不能靠编译结果兜底。

## 零、结论速查

| 写法 | CH32V20x 的处境 | 处理 |
|---|---|---|
| 外设基址常量 | 与 STM32F10x **完全相同** | ✅ 可直接沿用 |
| 寄存器偏移 | 绝大多数一致；3 个外设尾部有增减 | ⚠️ 逐个核对 |
| 位带别名地址 | CH32 是 RISC-V，**无硬件位带** | 🔴 必须改写 |
| 位带宏 / 位带函数 | CH32 侧零定义 | 🔴 必须改写 |
| `NVIC->xxx` 直访 | CH32 换成 PFIC，成员名全不同 | 🔴 必须改用库接口 |

## 一、地址指针直访寄存器

### 1.1 为什么它比改名危险

改名写错，编译器报「未声明」；地址写错，**编译器一无所知**，程序照常烧录运行，
只是读写落到了别的寄存器上。这类错误通常表现为「某个功能莫名其妙不工作」，
排查成本极高。所以凡是用到裸地址的地方，都必须查表确认，而不是假定兼容。

- `GPIOE_BASE` = `0x40011800`

> ⚠️ `DBGMCU` 要单独说：CH32V20x 的调试停机控制**不是内存映射寄存器，而是 RISC-V
> CSR(0x7C0)**（`__get_DEBUG_CR` / `__set_DEBUG_CR` 用 `csrr`/`csrw` 访问，
> 见 `ch32v20x_dbgmcu.c`）。因此 `0xE0042000` 这个地址在 CH32 上**完全无效**，
> 裸地址访问必须改用 `DBGMCU_Config()`；读芯片 ID 也不是 `0xE0042000`，
> 而是 `0x1FFFF704`（`DBGMCU_GetCHIPID()`）。
> 另外 CH32 的 `DBGMCU_Config(x, ENABLE)` 是**整体覆写** CSR，STM32 是读-改-写：
> 单次调用 `DBGMCU_Config(A | B | C, ENABLE)` 两侧等价，
> 但**连续两次分开调用会互相清除**，合并成一次调用即可避免。

CH32 新增（STM32 工程不会用到）：`USBFS_BASE` = `0x50000000`, `OPA_BASE` = `0x40023804`, `EXTEN_BASE` = `0x40023800`

### 1.3 寄存器偏移对照

基址相同不等于偏移相同。下表按**成员声明顺序 + 类型宽度**算出每个寄存器的字节偏移，
逐偏移比对（`RESERVED` 填充占位，因此偏移与手册一致）：

| 寄存器结构体 | 两侧共有寄存器 | CH32 缺失 | CH32 新增 | 判定 |
|---|---:|---:|---:|---|
| `GPIO_TypeDef` | 7 | 0 | 0 | ✅ 偏移完全一致 |
| `AFIO_TypeDef` | 4 | 0 | 0 | ✅ 偏移完全一致 |
| `EXTI_TypeDef` | 6 | 0 | 0 | ✅ 偏移完全一致 |
| `RCC_TypeDef` | 10 | 0 | 2 | ⚠️ 尾部有增减 |
| `TIM_TypeDef` | 20 | 0 | 0 | ✅ 偏移完全一致 |
| `USART_TypeDef` | 7 | 0 | 0 | ✅ 偏移完全一致 |
| `SPI_TypeDef` | 9 | 0 | 1 | ⚠️ 尾部有增减 |
| `I2C_TypeDef` | 9 | 0 | 0 | ✅ 偏移完全一致 |
| `DMA_Channel_TypeDef` | 4 | 0 | 0 | ✅ 偏移完全一致 |
| `DMA_TypeDef` | 2 | 0 | 0 | ✅ 偏移完全一致 |
| `ADC_TypeDef` | 20 | 0 | 0 | ✅ 偏移完全一致 |
| `CAN_TypeDef` | 16 | 0 | 0 | ✅ 偏移完全一致 |
| `PWR_TypeDef` | 2 | 0 | 0 | ✅ 偏移完全一致 |
| `BKP_TypeDef` | 45 | 0 | 0 | ✅ 偏移完全一致 |
| `RTC_TypeDef` | 10 | 0 | 0 | ✅ 偏移完全一致 |
| `IWDG_TypeDef` | 4 | 0 | 0 | ✅ 偏移完全一致 |
| `WWDG_TypeDef` | 3 | 0 | 0 | ✅ 偏移完全一致 |
| `CRC_TypeDef` | 3 | 0 | 0 | ✅ 偏移完全一致 |
| `FLASH_TypeDef` | 8 | 0 | 1 | ⚠️ 尾部有增减 |

**偏移完全一致 16 个 / 有增减 3 个 / 未判定或缺失 0 个。**

> 表中「两侧共有寄存器」已排除 `RESERVED` 占位。STM32 侧设备头里有若干
> `#ifdef STM32F10X_CL` 之类的条件编译分支，会让结构体总大小看起来更大，
> 但**按寄存器偏移逐项比对，两侧共有的寄存器没有一个是错位的**。
> 例：`RCC` 两侧各有 12 个寄存器且偏移一一对应 —— CH32 的 `CFGR2` 同样位于 `+0x2C`。
>
> `CAN` 的 `sFilterRegister` 是**寄存器组**而非单个寄存器，两侧起始偏移相同（`+0x240`）。
> STM32 中容量型号为 14 个 filter bank、互联型为 28 个，CH32 固定 28 个；
> 裸地址写法 `+0x240 + n*16` 的算法一致，只要 `n` 在原型号的合法范围内即可。

### 1.4 尾部增减的明细

#### `RCC_TypeDef`

| 偏移 | STM32 | CH32 | 说明 |
|---:|---|---|---|
| `+0x28` | — | `AHBRSTR` | CH32 新增 |
| `+0x2C` | — | `CFGR2` | CH32 新增 |

#### `SPI_TypeDef`

| 偏移 | STM32 | CH32 | 说明 |
|---:|---|---|---|
| `+0x24` | — | `HSCR` | CH32 新增 |

#### `FLASH_TypeDef`

| 偏移 | STM32 | CH32 | 说明 |
|---:|---|---|---|
| `+0x24` | — | `MODEKEYR` | CH32 新增 |

> `SPI` 的 `HSCR`、`FLASH` 的 `MODEKEYR` 是 CH32 新增的寄存器；
> STM32 侧的 `KEYR2` / `SR2` / `CR2` / `AR2` 属 `STM32F10X_XL`
> **双 bank** 专用，在本比对口径（`STM32F10X_MD`）下不参与编译，故不出现在上表。
> 两种情况下，**两侧共有寄存器的裸地址都可以直接沿用**。

### 1.5 `TIM_TypeDef` 的双宽度访问

CH32 的定时器寄存器用匿名 union 同时暴露 16 位与 32 位两种写法，
因为 CH32 的 `TIM5` 是 32 位计数器（STM32F103 的 TIM5 是 16 位）：

```c
union {
    __IO uint32_t CNT_R32;          /* 32 位访问（CH32 新增） */
    struct {
        __IO uint16_t CNT;          /* 16 位访问（与 STM32 同义） */
        uint16_t      RESERVED9;
    };
};
```

两侧 `TIM_TypeDef` 的总大小与偏移完全一致（均为 80 B），
因此裸地址访问定时器寄存器**不需要改偏移**。
新增的 `*_R32` 系列是 CH32 独有的便利写法，STM32 代码不会用到。

### 1.6 处理规则

1. **外设基址数值：保持不动。**
2. **寄存器偏移：查 1.3 表。** 标记 ✅ 的结构体，偏移可原样沿用；
   标记 ⚠️ 的结构体，只有 1.4 列出的那几个偏移需要留意，其余仍可沿用。
3. **优先把裸地址改回符号名。** 这是最省事的做法，也是唯一能让编译器替你兜底的做法：

```c
/* 改写前（编译器无法检查） */
*(volatile uint32_t *)0x4001080C |= (1 << 5);

/* 改写后（写错名字编译器立刻报错） */
GPIOC->OUTDR |= (1 << 5);
```

4. **`GPIOx_BASE` 之类的自定义宏可以保留**，但要把 `CRL`/`ODR`/`BSRR` 这些
   尾段名字换成 CH32 侧的名字（见 `02_structmap.md`）。

## 二、位带操作（bit-band）

### 2.1 CH32V20x 没有位带

位带是 ARM Cortex-M3 的硬件特性：把外设 / SRAM 的**某一个位**映射成一个 32 位字的地址，
读写那个字地址就等于原子地读写该位。STM32F103 的设备头里有这套定义：

| 宏 | STM32 取值 | CH32 |
|---|---|---|
| `PERIPH_BB_BASE` | `0x42000000` | **不存在** |
| `SRAM_BB_BASE` | `0x22000000` | **不存在** |

CH32V20x 是 RISC-V 内核，**整颗芯片没有任何位带硬件**。
对 `0x42000000` 段的读写没有定义，不能依赖。
CH32 的库源码里也找不到一处位带用法 —— 它自己全部改成了读-改-写
或专用置位/清零寄存器，这就是移植时应当照抄的思路。

作为对照，STM32 标准外设库**内部**就有 37 处位带操作，分布在：

| 源文件 | 位带宏数量 |
|---|---:|
| `stm32f10x_bkp.c` | 5 |
| `stm32f10x_cec.c` | 4 |
| `stm32f10x_gpio.c` | 2 |
| `stm32f10x_pwr.c` | 3 |
| `stm32f10x_rcc.c` | 12 |
| `stm32f10x_sdio.c` | 10 |
| `stm32f10x_wwdg.c` | 1 |
| **合计** | **37** |

这些是库内部的实现细节，用户无需处理。**列出它们是为了说明：
位带在 STM32 上不是罕见技巧，用户代码里出现位带的概率不低。**

### 2.2 位带用法的四种形式

| 形式 | 典型写法 | 识别特征 |
|---|---|---|
| A 库内部式 | `#define CR_HSION_BB (PERIPH_BB_BASE + (CR_OFFSET*32) + (HSION_BitNumber*4))`<br>`*(__IO uint32_t *)CR_HSION_BB = 1;` | 宏名以 `_BB` 结尾；含 `PERIPH_BB_BASE` |
| B 通用位带宏 | `#define BITBAND(addr,bit) ((addr & 0xF0000000)+0x2000000+((addr & 0xFFFFF)<<5)+(bit<<2))` | 出现 `0x2000000` / `0xF0000000` / `<<5` 与 `<<2` |
| C 纯字面地址 | `*(volatile uint32_t *)0x42420000 = 1;` | 地址落在 `0x42000000`~`0x43FFFFFF`（外设）或 `0x22000000`~`0x23FFFFFF`（SRAM） |
| D SRAM 变量位带 | `BIT_ADDR(&flag, 3) = 1;` 其中 `flag` 是普通变量 | 同上，但取址对象是变量不是外设 |

### 2.3 别名地址反解

形式 A / C 里的别名地址可以反解出「它到底在操作哪个寄存器的哪一位」，
公式（STM32 官方映射关系的逆运算）：

```
偏移 = (别名地址 - 0x42000000) >> 5
位号 = ((别名地址 - 0x42000000) >> 2) & 0x1F
原寄存器地址 = 0x40000000 + 偏移
```

例：`0x42420000` → 偏移 `0x21000` → 寄存器 `0x40021000`（`RCC_CR`），位号 `0`
（`HSION`）。

### 2.4 转换方案总表

| 操作 | 原 STM32（位带） | 改后 CH32（首选） | 改后 CH32（无专用寄存器时） |
|---|---|---|---|
| GPIO 置位 | `*(uint32_t*)BITBAND(&GPIOA->ODR,5) = 1` | `GPIOA->BSHR = (1 << 5)` | `GPIOA->OUTDR \|= (1 << 5)` |
| GPIO 清零 | `*(uint32_t*)BITBAND(&GPIOA->ODR,5) = 0` | `GPIOA->BCR = (1 << 5)` | `GPIOA->OUTDR &= ~(1 << 5)` |
| GPIO 读引脚 | `*(uint32_t*)BITBAND(&GPIOA->IDR,5)` | `(GPIOA->INDR >> 5) & 1` | 同左 |
| 普通外设置位 | `*(uint32_t*)BITBAND(&RCC->CR,0) = 1` | — | `RCC->CTLR \|= (1 << 0)` |
| 普通外设清零 | `*(uint32_t*)BITBAND(&RCC->CR,0) = 0` | — | `RCC->CTLR &= ~(1 << 0)` |
| SRAM 变量置位 | `*(uint32_t*)BITBAND(&var,3) = 1` | — | `var \|= (1 << 3)` |

**注意「首选」与「次选」的差别**：`BSHR` / `BCR` 是硬件级的原子操作，
与位带的原子性完全等价，应当优先使用；读-改-写则不具备原子性（见 2.7）。

### 2.5 GPIO：`BSHR` / `BCR` 等价替代

CH32 的 GPIO 与 STM32 偏移完全一致，但**最后两个寄存器的语义分工不同**：

| 偏移 | STM32 名称 | STM32 作用 | CH32 名称 | CH32 作用 |
|---:|---|---|---|---|
| `+0x0C` | `ODR` | 输出数据 | `OUTDR` | 输出数据 |
| `+0x10` | `BSRR` | 低 16 位写 1 置位<br>**高 16 位写 1 清零** | `BSHR` | 写 1 置位<br>（头文件只定义了 `BS0`~`BS15`） |
| `+0x14` | `BRR` | 写 1 清零 | `BCR` | 写 1 清零 |

CH32 的官方用法是「置位用 `BSHR`、清零用 `BCR`」两个寄存器分工，
库函数 `GPIO_SetBits` → `GPIOx->BSHR = GPIO_Pin`，
`GPIO_ResetBits` → `GPIOx->BCR = GPIO_Pin`。

> 🔴 **静默陷阱**：STM32 代码里的清零有两种写法，
> `GPIOA->BRR = (1 << 5)` 和 `GPIOA->BSRR = (1 << (5 + 16))`。
> 后一种在改名成 `GPIOA->BSHR = (1 << (5 + 16))` 之后，
> **寄希望于 CH32 的 `BSHR` 高 16 位也具备清零语义** —— 这一点在 CH32 头文件中
> 没有定义（只有 `GPIO_BSHR_BS0`~`BS15`），官方例程也从不这样用。
> 稳妥做法是一律改成 `GPIOA->BCR = (1 << 5);`。

### 2.6 其它外设：读-改-写 与 RISC-V 原子指令

除 GPIO 外，多数外设没有「写 1 置位」的专用寄存器，只能读-改-写。
CH32 库自己就是这么做的，可以照抄：

| STM32 库中的位带写法 | CH32 库中的等价写法 |
|---|---|
| `PWR_BackupAccessCmd`：`*(__IO uint32_t *)CR_DBP_BB = NewState;` | `PWR->CTLR \|= (1 << 8);` / `&= ~(1 << 8)` |
| `RCC_HSICmd`：`*(__IO uint32_t *)CR_HSION_BB = NewState;` | `RCC->CTLR \|= (1 << 0);` / `&= ~(1 << 0)` |

如果原来的位带用法**依赖原子性**（例如同一个标志位会被中断服务程序和主循环同时修改），
读-改-写会引入竞态。CH32 的内核头 `core_riscv.h` 提供了 RISC-V 原子指令的封装，
可以直接用（`ch32v20x.h` 已经 include 了 `core_riscv.h`，无需额外包含）：

| 用途 | 函数 | 说明 |
|---|---|---|
| 原子置位 | `__AMOOR_W(addr, mask)` | 读改写，返回操作后的值 |
| 原子清零 | `__AMOAND_W(addr, mask)` | 掩码取反后与 |
| 原子异或（翻转） | `__AMOXOR_W(addr, mask)` | |
| 原子加 | `__AMOADD_W(addr, val)` | |
| 原子交换 | `__AMOSWAP_W(addr, val)` | |

```c
#include "ch32v20x.h"        /* 已含 core_riscv.h */

/* 原 STM32 位带写法：*(__IO uint32_t *)CR_HSION_BB = 1;  —— 原子 */
__AMOOR_W((volatile int32_t *)&RCC->CTLR, (int32_t)(1u << 0));   /* 原子等价 */

/* 清零 */
__AMOAND_W((volatile int32_t *)&RCC->CTLR, (int32_t)~(1u << 0));
```

> 返回值语义与位带不同：位带读回来的是「该位的值」，这几个封装返回的是**操作后的整个寄存器值**。
> 地址必须 4 字节对齐。

### 2.7 SRAM 变量的位操作

形式 D（对普通变量做位带）在 STM32 上常被当作「廉价的原子位操作」使用，
典型场景是主循环与中断共享的标志变量。CH32 上没有位带，处理方式：

| 场景 | 处理 |
|---|---|
| 单上下文（仅主循环，或仅中断内） | 直接用 `\|=` / `&= ~`，无风险 |
| 跨上下文，但读改写彼此不冲突 | 用 `\|=` / `&= ~`，配合 `volatile` |
| 跨上下文且需要原子 | `__AMOOR_W` / `__AMOAND_W`，或关中断临界区 |

```c
/* 用原子指令做标志位置位 */
__AMOOR_W((volatile int32_t *)&Flag, (int32_t)(1u << 3));
```

> 如果拿不准是否存在跨上下文竞争，**应当向用户确认**，不要自行判断后静默改写 —— 
> 位带原本的原子性被去掉，属于会改变程序行为的改动。

## 三、中断控制器的寄存器直访

STM32 代码里常见 `NVIC->ISER[0] = ...`、`NVIC->IP[x] = ...` 这类直访。
CH32 的中断控制器叫 **PFIC**，设备头里给了别名 `#define NVIC PFIC`，
但两者的寄存器布局**完全不同**：

| 用途 | STM32（Cortex-M3 NVIC） | CH32（PFIC） |
|---|---|---|
| 使能中断 | `NVIC->ISER[n]` 写 1 生效 | `NVIC->IENR[n]` 写 1 生效 |
| 关闭中断 | `NVIC->ICER[n]` | `NVIC->IRER[n]` |
| 挂起 | `NVIC->ISPR[n]` | `NVIC->IPSR[n]` |
| 解挂 | `NVIC->ICPR[n]` | `NVIC->IPRR[n]` |
| 优先级 | `NVIC->IP[x]`，一字节，有效位在高位 | `NVIC->IPRIOR[x]`，一字节，直接写数值 |
| 活动状态 | `NVIC->IABR[n]` | `NVIC->IACTR[n]` |

好消息是**成员名不同，写错会直接编译报错**（`PFIC_Type` 里没有 `ISER`），
所以这一类属于 fail-fast，不会静默出错。遇到报错时改用库接口即可：
`NVIC_EnableIRQ()` / `NVIC_DisableIRQ()` / `NVIC_SetPriority()` / `NVIC_Init()`。

优先级数值的含义与 STM32 不同（CH32 按「是否开启中断嵌套」分两组，
取值范围 0~1 / 0~3 或 0~7），详见 `05_migration-rules.md` 第三节第 1 项。

## 四、核对清单

在用户代码里搜索以下模式，逐条过一遍：

| 搜索模式 | 含义 | 动作 |
|---|---|---|
| `0x4000` / `0x4001` / `0x4002` 开头的地址 | 外设基址或寄存器地址 | 利用 1.2 / 1.3 确认；能改回符号名就改 |
| `0x42` / `0x43` 开头的地址 | 外设位带别名地址 | 用 2.3 反解，按 2.4 改写 |
| `0x22` / `0x23` 开头的地址 | SRAM 位带别名地址 | 按 2.7 改写 |
| `PERIPH_BB_BASE` / `SRAM_BB_BASE` | 位带基址 | 该宏在 CH32 侧不存在，必然编译报错 |
| `_BB` 结尾的宏名 | 位带别名宏 | 查 2.3 表 |
| `BITBAND` / `BIT_ADDR` / `MEM_ADDR` | 通用位带宏 | 按 2.4 改写整组宏 |
| `<< 5` 与 `<< 2` 同时出现 | 位带地址换算 | 按 2.4 改写 |
| `BSRR =` 且含 `+ 16` 或 `<< 16` | GPIO 高 16 位清零写法 | 改成 `BCR =`（见 2.5） |
| `NVIC->` | 中断控制器直访 | 改用库接口（见第三节） |
| `0xE0042000` | STM32 DBGMCU 地址 | CH32 上无效，改用 `DBGMCU_Config()`（见 1.2 的 DBGMCU 说明） |
| `*(volatile` / `*(__IO` | 指针直访寄存器 | 确认偏移后决定是否保留 |

确认无遗漏后，编译通过仍不代表完成 —— 裸地址与位带的错误不会在编译期暴露，
**必须在真实硬件上验证相应功能**。
