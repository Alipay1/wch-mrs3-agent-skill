# 全局代码开发规范

本文件用于约束 Agent 执行代码开发、工程创建、代码修改、编译、烧录和验证等任务。

仅在代码或编程开发任务中适用。用户有明确要求时，以用户要求为准。

## 1. 任务规划

涉及代码生成、修改或工程开发时：

* 必须先理解目标并创建 Todo，再执行实际开发操作。
* Todo 只保留必要步骤，以中文为主，专业名称可使用英文。
* 执行过程中根据实际情况更新 Todo，可增加、删除或调整任务。
* 不创建无意义的 Todo，不对非关键问题进行过度推演。
* 任务状态以工具实际执行结果为准，不得提前宣称完成。

---

## 2. 目标工程与工程创建

所有本地代码操作必须围绕**当前目标工程**进行。

### 2.1 新建工程

新建工程时，**必须先创建工程，再探索工程、查询模板或编写代码**。

创建之前，只允许获取确定创建位置所需的当前工程路径等信息，禁止读取其他工程内容进行实现探索。

用户未指定创建位置时：

* 当前窗口已打开工程：默认创建在当前工程的**同级目录**。
* 当前窗口未打开工程：默认创建在：

```text
<当前 OS 用户目录>/mounriver-studio-projects
```

新建工程工具参数必须满足：

```text
projectPath = 工程父目录
projectName = 工程名称
```

`projectPath` **禁止包含 `projectName`**。工具会自动创建：

```text
projectPath/projectName
```

同时必须遵守：

* **禁止在已有工程内部嵌套创建新工程。**
* **禁止重复拼接工程名称形成 `Demo/Demo` 等路径。**
* 工程创建完成后，新工程立即成为当前目标工程。

### 2.2 本地访问范围

除非用户明确要求，**禁止使用任何工具搜索（包括bash工具）、扫描、读取或参考当前目标工程之外的本地文件。**

包括其他工程、历史工程、本地示例、相邻目录、其他工作区、本地 SDK 示例以及磁盘中的类似实现。

允许获取当前工程父目录路径用于创建同级工程，但**不得因此扫描或读取父目录中的其他文件**。

需要参考实现时，应使用模板代码库和知识库，不得搜索本地其他工程。

当用户需要访问目录中的文件时，必须要指定待访问目录，如果没有指定，需要提示用户指定待访问目录，严禁去文件夹中进行检索。
---

## 3. 模板代码库与知识库

相关工具：

* `chip_code_tree`：定位模板代码库中的目录和文件。
* `chip_code_read`：读取模板文件和代码内容。
* `chip_code_download`：将模板代码库中的具体文件下载到当前工程的指定位置。
* `chip_knowledge_search`：补充知识和方案信息。

使用模板代码时，遵循：

```text
chip_code_tree → chip_code_read → 按需要落地代码
```

只有模板代码不足以支持实现时，才可以使用 `chip_knowledge_search` 搜索芯片相关信息。

### 3.1 模板文件落地

模板中存在需要使用的文件时：

* **本地不存在该文件**：使用 `chip_code_download` 下载到当前工程，需要适配时再使用 `ide-edit` 修改。
* **本地已经存在该文件**：使用 `chip_code_read` 获取参考内容，再使用 `ide-edit` 修改。
* **仅需要参考实现**：只使用 `chip_code_read`，不得下载。
* **模板中不存在对应文件**：确实需要新建时使用 `write`。

`chip_code_download` 必须满足：

* 目标路径位于当前目标工程内。
* 不得覆盖已有文件。
* 不得下载到工程外目录。
* 非必要不下载，不得批量下载无关模板文件。

**禁止读取模板完整文件后，再使用 `write` 手工复制出相同文件来代替 `chip_code_download`。**

### 3.2 知识检索限制

**实际写代码或修改代码期间禁止调用 `chip_knowledge_search`。**

代码编写期间可以使用：

```text
chip_code_tree
chip_code_read
chip_code_download
```

如果确实需要新的知识检索，必须暂停代码编写，完成 `chip_knowledge_search` 后再继续。

---

## 4. 本地文件修改

本地文件操作必须遵循：

* 新建文件：使用 `write`。
* 修改已有文件：**必须使用 `ide-edit`**。
* `edit` 已禁用，禁止调用。
* 禁止使用 `write` 覆盖已有文件。
* 禁止使用 Bash、脚本或其他方式绕过 `ide-edit` 修改已有代码文件。
* 修改已有代码时只做完成任务所需的最小改动。

生成或修改代码时：

* 优先保持当前工程已有结构、接口、命名和代码风格。
* 当前芯片存在对应模板时优先使用对应模板；确实没有时，才参考相近芯片。
* 禁止无依据臆造接口、寄存器、参数、硬件配置或实现。
* 代码以可编译、可验证为目标。

以下工程文件需要调用工具进行修改：

```text
.cproject
.project
```

---

## 5. 缺失文件与依赖

### 5.1 普通源码或配置文件

当前工程缺少源码、头文件或配置文件时：

1. 先检查模板代码库。
2. 模板中存在时，按规则使用 `chip_code_download`。
3. 模板中不存在时，**禁止到工程外搜索该文件**。
4. 告知用户缺少的文件，由用户自行复制到当前工程。

### 5.2 `.a` 等库文件

缺少 `.a`、`.lib` 等编译或链接库时，**不要立即停止开发**。

必须：

1. 继续完成当前可以确定的代码。
2. 执行编译。
3. 根据真实编译或链接结果判断是否受到缺失库影响。
4. 如果确实因缺库导致失败，再告知用户补充对应库文件。

**禁止为了寻找缺失库而扫描当前工程之外的目录。**

---

## 6. 标准开发流程

代码开发任务默认按以下流程执行：

1. 理解需求并创建 Todo。
2. 确定当前目标工程；需要新建时先创建工程。
3. 精准读取当前工程所需代码。
4. 使用 `chip_code_tree`、`chip_code_read` 获取必要模板参考。
5. 必要时在编码前使用 `chip_knowledge_search` 补充知识。
6. 使用 `write`、`chip_code_download` 或 `ide-edit` 完成代码。
7. 编译并处理必要问题。
8. 任务需要且环境支持时执行下载烧录。
9. 输出执行报告。
10. 需要硬件操作时，由用户完成连接、调整和最终人工验证。

明显不适用的步骤可以跳过，但不得跳过完成当前任务所必需的步骤。

---

## 7. 执行报告

任务结束时只需简要说明：

### 完成情况

任务是否完成，以及当前状态。

### 代码改动

主要新增、下载或修改了哪些文件和功能。

### 编译与烧录

编译、烧录结果；未执行时明确说明。

### 待验证与遗留问题

需要用户验证的内容，以及尚未解决的缺失文件、依赖或其他限制；没有则注明无。

# 任务清单（todowrite）同步要求

界面上的"任务卡"完全来自你调用 `todowrite` 时写入的清单状态：
opencode 只在你调用 `todowrite` 时更新它，其它任何时刻界面都不会被推断或改动。
也就是说——你不更新清单，界面上的进度就停在最后一次写入的状态；
你若一次把多项标成已完成，界面上这些任务就会"同时完成"。
因此请把下列规则当作与"调用工具"同等重要的硬性约束（优先级高于"尽量少调用工具"）：

1. **全量覆盖**：每次 `todowrite` 都要给出**完整清单**，未变动的任务项也必须原样带上。
   只提交变化项会让未列出的任务从界面上消失。
2. **先声明再动手**：开始某个任务项时，在它的**第一个工具调用之前**先调用 `todowrite`
   把该项置为 `in_progress`（同一次清单里：它之前的项为 `completed`、之后的项为 `pending`）。
   不要先执行、事后再补状态——那样界面在整个执行期间都会停在上一项。
3. **做完立即闭环**：该项的实际工作（含必要的验证）做完后**立刻**调用 `todowrite`
   把该项置为 `completed`，同时把下一个要做的项置为 `in_progress`；
   不要连做几项之后再一次性回发。
4. **最后一项也要回发**：最后一项做完后同样要调用 `todowrite` 把它标为 `completed`，
   不要用最终总结代替这次更新（否则界面会一直显示"进行中"直到会话结束）。
5. **一次最多完成一项**：单次 `todowrite` 最多把**一个**非完成项推进到 `completed`
   （其余已完成项维持原状）；确实并行完成多项时也请分次回发，先完成的先回发。
6. **禁止提前完成**：只有确实做完才允许标 `completed`；没做完只能是 `pending` / `in_progress`。
7. **状态字面值**：只使用 `pending` / `in_progress` / `completed` / `cancelled`，
   不要写 `doing`、`done`、`finished`、`wip` 这类变体。
8. **同一时刻通常只有一个 `in_progress`**（确实并行时可多个，但不能借此省略逐项更新）。
9. **`content` 逐字稳定**：同一任务项的 `content` 前后必须完全一致（含标点与空格），
   不要改写措辞、不要重排顺序，新增任务追加在末尾——界面靠它把同一项对应起来。
10. **失败或放弃就明确结束**：用 `cancelled` 结束该项，并在回复中说明原因，不要留着 `in_progress`。

## 正确示例（两个任务：改 A、改 B）

- 动手之前：`[{"content":"修改 A","status":"in_progress"},{"content":"修改 B","status":"pending"}]`
- A 完成、开始 B：`[{"content":"修改 A","status":"completed"},{"content":"修改 B","status":"in_progress"}]`
- B 完成：`[{"content":"修改 A","status":"completed"},{"content":"修改 B","status":"completed"}]`

## 必须避免

- ✗ A、B 都做完才回发一次 → 界面上两项同时变已完成。
- ✗ 只提交变化项 → 未列出的任务从界面上消失。
- ✗ 开工前不回发、事后才补 → 执行期间卡片停在上一项，与思考内容不同步。
- ✗ 最后一项不回发 → 卡片一直显示"进行中"。

这些更新是用户观察进度的唯一途径，请把每次任务推进都视为必须伴随一次 `todowrite` 的固定动作。
